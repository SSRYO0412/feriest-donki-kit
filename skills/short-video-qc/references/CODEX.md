# Codex の呼び方（実測済み・2026-07-29検証）

## ★★★ 最重要: 全数観察に MCP を使ってはいけない

**`mcp__codex-cli__codex` はリクエストを直列化する。** 1メッセージに5本のツール呼び出しを並べても、
前のスライスが終わって約15秒後に次が始まり、**重なりがゼロ**であることを実測で確認した。

したがって:
- **サブエージェントを何個立てても速くならない**（全員が同じMCPサーバを叩くため）
- **Codexに内部サブエージェントを立てさせる案も同様**（MCP経由である限り直列）
- **全数観察は必ず `scripts/codex_parallel.sh`（CLI直叩き・バックグラウンド並列）で行う**

MCPを使ってよいのは、**1回で完結する少量の問い合わせ**だけ（設計案レビュー・採点・個別確認など）。

## 実測値（17_v21.mov・2949枚）

| 方式 | スループット | 2949枚の所要 | 備考 |
|---|---|---|---|
| MCP経由（直列） | 0.36枚/秒 | 約2.3時間 | 並列化不能 |
| CLI 10並列（20枚/本） | 2.9枚/秒 | 約17分 | 起動オーバーヘッドが支配的 |
| **CLI 20並列（148枚/本）** | **10.8枚/秒** | **4分33秒** | **被覆率100%・欠番0で検証済み** |

**スライスは大きいほど良い。** 1プロセスの起動に約20秒かかるため、
20枚/本では0.35秒/枚、148枚/本では0.093秒/枚と**約4倍**の差が出る。
20並列 × 150枚前後が良いバランス。

3本（9,863枚）の実運用推定は**約15分**。

## フレーム抽出は1パスで行う

seekを毎回やる方式は桁違いに遅い。`fps` フィルタの1パス抽出を使う（2949枚で**約2秒**）。

```bash
ffmpeg -v error -y -i <mp4> -vf "fps=30,scale=300:-2" -q:v 4 <dir>/f%05d.jpg
```

`fps=30` が全フレーム。知覚的検査だけなら `fps=10`（0.1秒刻み）でも
テロップの切れ目は検出できることを実測済みだが、**ゲートG21/G22は全フレームを要求する**。
落とす場合は理由をdecisions.jsonに記録し、報告書に分母/分子で明記すること。

## 基本設定（これ以外は動かない）

- **model: `gpt-5.5` 固定**。既定の gpt-5.3-codex ほか enum のモデルは ChatGPT アカウントでは全て 400 エラー
- CLI: `codex exec --skip-git-repo-check --sandbox read-only -m gpt-5.5 "<prompt>"`
- MCP: `mcp__codex-cli__codex`（model: "gpt-5.5" / sandbox: "read-only"）
- reasoningEffort: 観察は `low`〜`medium`、レビュー・採点は `medium`〜`high`
- 認証切れ（invalid_grant）時はユーザーに `codex login` を依頼する（Claudeからは直せない）
- macOSに `timeout` コマンドは無い。使わないこと

## 手順①: 全数観察（CLI並列・省略不可）

```bash
# 1. 1パス抽出
ffmpeg -v error -y -i <mp4> -vf "fps=30,scale=300:-2" -q:v 4 <frames>/f%05d.jpg

# 2. 20並列で全数観察（スライス分割は本スクリプトが行う）
bash ~/.claude/skills/short-video-qc/scripts/codex_parallel.sh <frames> <out> 20 "<動画の説明>"

# 3. ★被覆を機械照合（自己申告のCOUNTは証拠にならない）
python3 ~/.claude/skills/short-video-qc/scripts/coverage_verify.py <frames> <out> --out qc/coverage_report.json
#    → 欠番があればスライス名が出るので、そのスライスだけ再実行して再照合
```

**coverage_verify が PASS するまでゲートは通らない。** 並列実行では、あるスライスが
レート制限や異常終了で落ちても「他が成功しているので全体は成功」に見えてしまう。
これを機械で潰すのが3の役割。

## 手順②: 敵対的レビュー（MCP可・1回で完結するため）

対象は3つ。①設計案 ②テロップの区切り ③完成動画（観察結果を渡す）。

```
ショート動画の設計案をレビューしてください。あなたの役割は敵対的レビュアーです。
通すことではなく、欠陥を見つけることが仕事です。

- スロット表: <slots.jsonのパス>
- 各スロットの候補フレーム: <ディレクトリ>
- 参考動画の文法: <ref_cut_grammar.json / ref_telop_grammar.json のパス>

観点:
1. 各スロットのスコアは妥当か。恣意的な点付けはないか
2. より良い候補（別の時間窓・別の素材・「置かない」）を見落としていないか
3. 同じ被写体が近接して繰り返されていないか
4. テンポへの影響（画が変わらない時間）を悪化させる選択はないか
全指摘に重要度（高/中/低）を付けてください。
```

## 手順③: 独立採点（MCP可）

```
ショート動画を採点してください。制作経緯は一切伝えません。素材は次の3点のみです。
1. 完成動画の全フレーム観察結果: <出力ディレクトリ>
2. 参考動画のフレーム: <ディレクトリ>
3. 採点基準: <基準の本文>

各項目の点数と減点理由を、フレームのファイル名を根拠に挙げて出してください。
制作者を励ます必要はありません。視聴者として厳しく採点してください。
```

## 指摘の記録（握りつぶし禁止）

`qc/codex_review_*.json` の各指摘レコード:
```json
{
  "id": "R-003", "severity": "高", "target": "f01234.jpg (41.1s)",
  "issue": "『走行13万キロ』でメーターが見えず説得力がない",
  "response": "採用", "reason": "メーターの寄り素材が存在するため差し替える",
  "action": "slots.json のスロット8を更新"
}
```
- `response` は 採用/却下 の二択。**却下の場合は根拠をCodexに返し、その応答も記録する**
- 全指摘に response が付くまで次工程に進めない

## レンダーゲートへの組み込み

```python
review = json.load(open("qc/codex_review_design.json"))
if review["input_sha256"] != sha256_of(cutlist, telops, inserts):
    raise SystemExit("Codexレビューが古い。設計を変えたら再レビューしてからレンダーする。")
```

## Codexの誤りの実例（応答を鵜呑みにしない）

- 低解像度グリッドで人名を誤読した（「国吉」→「固吉」）。**固有名詞は実物のテロップ画像で裏取りする**
- 白飛びした車体を別車と誤認した（採点サブエージェント側の例）。**疑わしい判定は元素材の原寸で確認する**
- 体感の自己申告（「8〜12枚が安全」）を鵜呑みにして上限を決めつけた。**能力の上限は必ず実測する**
