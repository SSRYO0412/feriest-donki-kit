# 編集テンプレ — EDLは Claude(=このスキルを動かす私)が直接 authoring する

## 大原則
**「どの発話を使うか／テロップに何を書くか」という編集判断は、別のLLM API を呼ぶのではなく、このスキルを実行している Claude 自身が行う。** スキルを動かすのは毎回 Claude Code なので、編集の脳＝実行中の私。APIキー/SDK/別LLM呼び出しは不要。

役割分担:
- **Claude(私)**: 文番号スクリプトを読み、下記テンプレに沿って **edl.json を直接書く**(クリップ選定＋テロップ文言＋verdict語の特定)
- **コード**: 文字起こし(window_transcribe)→文番号スクリプト生成(make_script.py)→cut/build/render。**秒精度はコードが単語境界にスナップ**(私に秒精度を求めない)

検証済み: 44文スクリプトだけから私が起こしたEDLが、手作りEDLとほぼ一致(構造・テロップ・verdict時刻まで)。この分業で品質が出る。

## 手順
1. `make_script.py words.json` → 文番号付きスクリプト(`[idx] start-end text`)を出す
2. 私がスクリプト＋下記「編集構造」を読み、**edl.json** を書く(各クリップ= 連続する文の範囲＋テロップ authoring)
3. in/out は文の start/end に lead-in 0.2s / tail 0.25s。verdictクリップは答えの語の**生の表記**(誤認含む: 要相談→「洋相談」等)を `verdict_word` に入れ、コードが単語時刻を引く
4. **★カット粒度セルフチェック（設計直後・必須）**: クリップ数÷合計尺(分)を参考の cuts/min（detect_shots 複数閾値スイープの実測）と比較。±30%を外れたら書き直し。**参考の最長ショットを超えるスパンは `圧縮ジャンプ` で複数クリップに刻む**（文中でも文節境界で間・フィラー・冗長を落とす。「一文だから丸ごと」は反面教師=17.8秒撮って出しで差し戻された）。カット点は語境界±0.15s。
5. **★変速 authoring**: pace=`詰め` の説明/列挙モノローグは clip に `"speed": 1.3〜1.5`、判定/オチ/溜めは speed を付けない(=1.0)。**seEvents はテロップイベント単位**（逐次行の各出現・判定・大カット切替）で、at は出力時間軸（変速後）で書く。
6. ユーザーに edl.json を提示し承認を得てから cut/build/render(承認ゲート)

## 編集構造(★参考動画ごとに Phase 1 で導出。下は「採用ジャッジ動画」の例)
ジャンル= 司会が候補者プロフィール提示→パネルが採用/不採用/要相談を即答→理由/オチ。
- **intro(1本, ~5s)**: 冒頭フック。店名+「こんな人採用できる？」等の前提
- **候補者ブロック(3〜5人, 各12〜22s)**: 各候補について
  - **profile**: 年齢/経歴/性別 + 一番ツッコミどころのある属性(少年院/夜職/前科/恋愛リアリティ等)
  - **verdict**: パネルの答え(採用/不採用/要相談)。必ず答えの発話を含む文を選ぶ
  - **punch / reason**: 一番面白い理由・やりとり
- **outro(1本, ~5-8s)**: 応募案内/インスタ誘導のCTA

選定ルール: 驚き/物議の候補を優先(エンゲージ↑)。冗長な雑談は捨てテンポ良く。合計60〜90s目安。
詳細は下記「★カット選出ルール12項」に従う。

## ★カット選出ルール（素材のどこを「有り」とするか・12項）
実証ベース: 差し戻された v1 と合格した手動編集は元素材562秒からの採用率がほぼ同じ(15-17%)なのに、
**選出の質**が別物だった（Q&Aを間奏ビートに昇格・CTAを拾う・前振りを削って核だけ・グダグダを捨てて
綺麗な判定へ直行・プロフィール読み上げをカード化）。毎回、以下をルールとして適用する。

### A. ブロック設計（何をビートにするか）
1. **ビート数パリティ**: 参考のブロック数（弧＋間奏）を数え、素材側で同数を組む。素材の弧（候補/トピック）が
   足りなければ **Q&A・掛け合い・リアクションを「間奏ビート」に昇格**させて埋める。総尺だけ合わせて
   ブロック数が少ないと1ブロックが肥大する（実例: 候補1ブロックが35.5秒に肥大して差し戻し）。
2. **1ブロック尺予算**: 参考の弧尺分布（例: 12〜22s）を各ブロックの上限にする。超過は**まず選出で削る**
   （圧縮ジャンプ・変速は微調整であり、選びすぎの救済に使わない）。
3. **機能カバレッジ必須**: フック/文脈提示/判定×N/理由/CTA という参考の機能ビートを素材側で全て埋める。
   **参考にCTAがあれば素材からCTA発話を必ず探す**（実例: CTA素材が存在したのに捨てて減点。無ければテロップで作る）。

### B. 発話の採用基準（どの文を有りとするか）
4. **優先度は〈判定・断言・数字・固有名詞〉**: 1文で立つ発話を最優先（「採用で」「全員そうだと思います」「客単価13000円」）。
5. **質問は核だけ・回答は1〜2文**: ヘッジ（「言いづらいかもしれないんですけど」）・前振り・文脈説明を削り、
   疑問文の核＋具体策/断言の回答だけ残す（合格実例: 前振り4文を削ってQ+A計6秒に圧縮）。
6. **情報価値のみの解説は捨てる**: 技術詳細・制度説明・内輪話は、**視聴者ペルソナの関心軸**（下記）に
   合うものだけ拾う（合格実例: 4つのQ&Aトピックから関心軸に乗る2つだけ採用）。
7. **定型情報はカード化**: テロップで代替できる情報（プロフィール等）に発話時間を使わない。**時間は感情に使う**。
8. **無条件で捨てるクラス**: 挨拶・フィラー・相槌・段取り/楽屋トーク・単独の「そうですね」。
9. **グダグダの整理（★参考準拠の条件付き）**: 結論が二転三転する/話者が画で特定できないやりとりは、
   **参考が「整った編集」なら捨てて一番クリーンな判定発話1つに絞る**（実例: 「しないらしいですね」の混乱を
   ツイストとして残して失敗、合格版は捨てて直行）。**参考が「生っぽい編集」**（グダグダ・素のやりとりを
   演出として残すタイプ）**なら参考と同じ粒度で残す**。どちらと判断したかの根拠を edl の note に明記する。

### B2. 談話整合（★意味の接続・選定の絶対制約）
文は「単体のパンチ力」でなく**談話の依存関係ごと**選ぶ。実証: 回答の頭「早くても別にそんなに」を
切り落として離職の質問に遅刻の答えが付いた／「そこの面では」の先行詞をスキップして指示語が宙に浮いた／
「あと、」「（〜だった）ら、」で文中・列挙の途中から入った——いずれも納品後にユーザーが即指摘。
1. **クリップ頭の接続詞・指示語ガード**: あと/でも/そこ/それ/そういうの/なので/(〜た)ら 等で始まる
   スパンは、先行文脈を含めるか、その語を含まない位置まで入りを下げる。
2. **Q&Aは対で完全形**: 答えが参照する前提を必ず質問側に含める。答えの頭の受け語を切らない。
3. **入り・出は文頭・文末**（語境界だけでは不十分。文中エントリ/イグジット禁止。意図的な文中切りは
   note に理由を明記した場合のみ）。
4. **★前提の未確立ガード**: 各クリップについて「**この文が前提にしている事実は、ここまでの映像で
   （音声または大テロップで）言及されたか**」を必ず自問する。ミニカードの小さな属性表示は「言及」に
   数えない。実証: 「早めに辞めてるなってところがあると思うんですけど」を、前サロンの話が一度も
   出ていない映像で使い差し戻し（元素材には「美容師歴1年目ってことなので」という前提発話が存在し、
   尺のためにそれを削ったのが原因）。前提が長すぎて含められないなら、その話題ごと捨てる。
   ※これはリンター(check_discourse.py)では検出できない=LLMの通読でしか拾えないクラス。
5. **選定確定後、組んだ台本を頭から通読して「会話として意味が通るか」を宣言してから cut に進む**
   （verification 1.9 意味整合ゲートの設計時実行）。クリップごとに前提ガード(4)を個別に答えること。

### C. 並べ替え（時系列より弧の形）
10. **発話はビートの核から使ってよい**（コールドオープン）。文脈は無音カードで前出し/後出しする。
11. **同種ブロックを連続させない**: 弧→間奏(Q&A)→弧の交互配置で単調さを崩す。

### D. 選出のセルフチェック（edl 承認提示に含める）
12. **ブロック数・各ブロック尺・機能カバレッジを参考と数値比較**して提示する。発話の採否は**相対評価**
    （同roleの候補発話を2つ以上並べて選ぶ・PRINCIPLES「主張と映像の一致」節準拠）。「まあ使えるしOK」の
    単独絶対評価をしない。

### 視聴者ペルソナと関心軸（Phase 1 で言語化・上記6番の判定基準）
参考分析の段階で「この動画を誰が最後まで見るか（ペルソナ）」「その人の関心軸」を1〜3行で言語化して
arc.json の meta に残す（例: 採用ジャッジ動画→求職者。関心軸=年齢/売上/職場の雰囲気/SNS）。
素材選出の6番はこの軸で判定する。**軸に乗らない深掘りは、情報として正しくても捨てる**。

**構成の再編集（素材の時系列に縛られない）**: 参考・合格実例が持つなら次の型をクローンする:
- **コールドオープン**: 判定/オチなど山から入り、文脈(プロフィール等)は無音声のテロップカードで前出しor後出し（実例: 冒頭8秒=フックカード→大プロフィールカードを黙って見せ、いきなり判定発話から始まる）
- **弧間の変化球**: 候補ブロックの間に Q&A/掛け合いを挟み単調さを崩す
- **CTA締め**: 応募/フォロー誘導の発話・テロップで締める
プロフィール等の「読み上げ」は、参考がカード表示だけで済ませているなら**発話を使わずテロップカードに置換**してよい（11.8秒の読み上げ→5.6秒の無音声カードで合格した実例）。

> 別ジャンルの参考動画なら、この「編集構造」を Phase 1 で取り直す(telop-spec と同じく、手順は再利用・構造は動画ごと)。

## テロップ authoring(telop-spec準拠・キーワード要約)
- hook: `{"type":"hook","small":"店名等","big":["行1","行2"],"hl":"big内の黄box強調行"}`
- profile: `{"type":"profile","lines":["年齢・経歴","性別等"],"hl":"パンチ属性(黄box)"}` ※発話を圧縮
- verdict: `{"type":"verdict","text":"採用|不採用|要相談"}` + `"verdict_word":"<生表記>"`
- verdict+理由: `{"type":"verdict_reason","text":"採用|..."}` + `"verdict_word"`
- punch(字幕のみ): `{"type":"caption_only"}`
- cta: `{"type":"cta","lines":["行1","行2","行3"]}`
字幕は build.py が文字起こしから自動生成(逐語)。profile/hook は発話を圧縮したキーワードにする。

## edl.json スキーマ(build.py が消費)
```json
{ "source":"/abs/master.mov","fps":30,"width":1080,"height":1920,
  "words_file":"words.json","fixes":{"夜食":"夜職",...},"palette":{...telop-spec...},
  "clips":[
    {"id":"c01","role":"intro","in":3.5,"out":8.95,"tel":{"type":"hook","small":"...","big":["..",".."],"hl":".."}},
    {"id":"c03","role":"verdict","in":24.9,"out":26.4,"tel":{"type":"verdict","text":"採用","vt":25.36}},
    {"id":"c04","role":"reason","in":27.0,"out":33.2,"speed":1.5,"tel":{"type":"caption_only"},
     "seEvents":[{"at":0.1,"type":"ding"}]},
    ...] }
```
verdictの `vt` は verdict_word の単語時刻(コードが算出)。
