> ★修正指示の大半は**既知の類型**に落ちます（0801 の修正12ラウンド＋敵対レビュー6件を分解して確認済み）。
> 類型ごとに「どの表を引く → 何を確かめる → どう実装する → 何で検証する」を固定してあります。
> 事前計算済みの表は `data/revision_aids/` にあり、**素材解析DBなしで DBあり時と同じ数値絞り込み**ができます。

## 使う表

| ファイル | 中身 | いつ引く |

| `data/revision_aids/alternatives.json` | 30スロット×軸別の代替候補 top5 ＋ 商材別極値リスト | 差し替え系の指示が来たら最初に |

## カメラ分類の読み方

`clip_profiles.json` / `alternatives.json` の `camera`:

| 値 | 意味 |
|---|---|
| `static` | 三脚級の静止 |
| `drift` | 手持ちの自然な揺らぎ（小さい流れ） |
| `handheld` | ぶれ主体（動き量よりジッタが大きい） |
| `pan_left/right/up/down` | 画面の流れの向き。★**カメラの向きはその逆**（pan_right = 被写体が右へ流れる = カメラは左へ振っている） |
| `zoom_in` / `zoom_out` | 寄っていく / 引いていく（前進・後退を含む） |

数値: `motion` = 平均の動き量[px/frame @160x120]・`jitter` = ぶれ成分。
0801 実績の目安: 「激しい」と採用された a0928 の該当秒が **8.2〜11.0**、静止扱いは **0.6 未満**。
（★当時の採用判断の実測値 8.18 が clip_profiles の同じ秒に再現されることを確認済み——測り方が当時と一致している）

## 類型別の手順（0801 で実際に来た指示に基づく）

### 型1 「白飛びしている / 明るすぎるので差し替え」

1. `alternatives.json` → 該当スロット → `白飛び回避`（white_max 昇順 top5）
2. ★白飛びは**絶対値でなく相対**。全ショットの白飛び率を並べ、1つだけ突出していないかを見る（0801 実例: c04 だけ 6.34%・他 0.00%）
3. 差し替え → 検証は `reference_match.py` の G90-9（完成画素で再測定）

### 型2 「もっと激しいカメラワークで」「安定した画にして」

1. `alternatives.json` → スロットの `動き最大` / `安定・静止`、または商材の `動き最大_top10` / `完全静止_top10`
2. ★この素材群の実測上限は決まっている（0801 では「激しい」の最大が motion≈8）。**無い動きは無い**——上限を超える要求は素材不足としてテロップ/構成で補う判断へ
3. 種類の指定（「ズームで寄っていく画」「左へ振る画」）は `カメラワーク種類別` / `camera_*_top` を引く
4. ★スロットの軸は **s34候補プール内**の並べ替え。当たりが無ければ商材全体の `動き最大_top10` →
   それも内容が合わなければ `clip_profiles.json` を秒単位で走査する。
   **c05 の実採用 a0928 はまさに候補プール外から、この走査に相当する探索で見つけた**
   （t=6〜8秒と15〜16秒に motion 8〜11 の山がある）。表に無い＝存在しない、ではない

### 型3 「被写体が中心にない / 見切れている / 全体が見えるカットに」

1. `alternatives.json` の候補行の `subject_center`（x_pct / y_pct）で一次絞り込み
   （0801 実例: ピザ中心 y=0.363 の素材 → y=0.516 の素材へ差し替えて解決）
2. ★subject_center は鮮鋭度重心の**近似**。必ず中央フレームを書き出して実画で確認
3. 収まらない場合はズーム側で調整（zoom は `112〜117` が参考の帯。外すなら waiver を書く）

### 型4 「人物が写っている」

1. `alternatives.json` → `人物なし`（person_count=0）
2. ★ラベルは食い違うことがある（人なし表記に素手が写っていた実例）。**手・指・映り込みまで実画で見る**

### 型5 「寄りで / 引きで」

1. `alternatives.json` → `寄り` / `引き`（shot_size で絞り済み）
2. 素材に無ければズームで作る（帯 112〜117、参考の冒頭パンチは 0F:100/4F:120/6F:110）

### 型6 「意味が合っていない / ○○が伝わらない」

1. `s34_FINAL3.json` の該当スロット候補を `matched` と action で見直す
2. ★動作レベルで一致させる（「触る」と「なぞる」は違う）。単語一致で選ばない
3. `__NO_INSERT__`（置かない）も常に候補に入れる

### 型7 「テンポが違う / カットを増やして・減らして」

1. `.fork/REFERENCE-TARGETS.json` の tempo が正（主判定は shots_per_telop=1.77±30%）
2. 分割は同一クリップ内の隣接時間で行う（候補行の t0/t1 から外側は `clip_profiles.json` で様子を見る）
3. 検証は G90-1〜5

### 型8 テロップ・強調・色・ズームの調整

素材選定は不要。`TELOP-SPEC.md` / `PREMIERE-RECIPE.md` / MOGRT パラメータ表へ。
検証は G90-6/7/13（様式・フチ・ΔRGB）。

## 表に無い指示が来たら

1. まず類型に本当に落ちないか読み直す（言い換えのことが多い）
2. 落ちなければ `clip_profiles.json` で粗く当たり（秒単位の数値地図）→ 疑わしい区間だけ
   ffmpeg でサムネ列を出して実画目視（`ASSETS.md` §3 のコマンド）
3. ★それでも決め手が無ければ「素材に無い」を数字で報告する（探索した範囲と件数を添えて）。
   探せば見つかる、と言わない——この案件では**不在の確定**も成果物です

## 検証（どの型でも共通）

```
実装 → 機械検算（隙間/重複/終端/run長/キー頭）
     → 書き出し → reference_match.py（完成画素で G90）
     → 修正台帳と修正記録DBに記録（★上書きしない・却下版も残す）
```
