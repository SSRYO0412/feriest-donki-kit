# プロソディ(抑揚)制御プレイブック — 制御手段のはしご

2026-07-02の実戦(関西弁UGC広告ナレーションの再現)で確立。タグ調整の試行錯誤で頭打ちになったときに読む。

## 根本原則: 制御粒度のミスマッチを認識する

Fish Audio等のタグは**感情・ムードレベルの粗い意味的制御**。以下は実測で確認済み:

- `[building rise, then sharp downward snap on final mora]` のような**音響仕様の記述タグは安定して効かない**。モデルは意味的に解釈し、雰囲気演技に変換してしまう
- `[light laugh]` `[chuckle]` `[smile in voice]` 等の演技指示タグは**意図しない笑い・変な感情(「謎の感情」)の混入源**。使わない
- タグは**置いた位置より後ろのテキストに効く**。文末に置いた語尾指定は無効(実測: 文末置き `[no elongation]` は効かず、最終語の直前に移すと語尾スロープが +362Hz/s → -511Hz/s に転換した)
- 単語レベルでタグを増やすほど制御できる、は幻想。タグ密度を上げると発話が不自然になる
- **1行あたり単純な感情語2〜3個まで**が経験的な上限(例: `[scoffing][fast]`)

## 生成呼び出しの単位

- **全行を1リクエストにまとめる**: 行間のつながり・トーンの一貫性は良いが、全体が均されてテンション差が出にくい
- **1行ずつ個別リクエスト**: 行ごとのテンション差は最大化するが、つなぎが不連続になり「毎行仕切り直し」感が出る
- 実戦では**まとめて1リクエスト(+タグを行ごとに強く差別化)が最も自然**と評価された。中間案として「感情のまとまり(2〜4行)ごとのバッチ」も有効
- 個別生成した場合は `ffmpeg -f concat` で結合できる。行間の間(ま)は無音パディングで後調整

## はしご(弱→強の順に上る)

### 1. 表記プロソディ(日本語特有・最初に使う最強レバー)
日本語ではタグより**表記そのもの**が抑揚を強く決める:

| 書き方 | 効果 |
|---|---|
| 「教えよ**っ**」(促音止め) | 言い切り・クリップされた語尾(glottal stop) |
| 「!?」「!?!?」 | 急上昇→即断ち |
| 「。」 | 自然な下降終止 |
| 「ー」「〜」 | 伸ばす(語尾伸び防止では**排除**する) |
| 「、」の位置 | ポーズ・息継ぎの誘導(breathタグより自然) |
| カタカナ表記 | 強調・平板読みの誘導 |

参考動画にテロップがあるなら、**テロップの表記(!! や !? の数まで)をそのまま使う**のが最も再現性が高い。

### 2. タグの規律
- 単純な感情語(excited / calm / scoffing / confiding 等)を2〜3個、行頭または対象スパンの直前に
- 音響仕様の英語長文・演技指示(laugh系)は書かない
- 変化点の直前に置く(タグは後続に効く)

### 3. 参照音声のキュレーション(クローンの既定値を作る工程)
- クローンモデルは参照クリップの話し方を「素の喋り方」として固定する。**参照に含まれない抑揚はタグで安定して出せない**
- **方言・文体は参照と一致させる(2026-07-02実測)**: 関西弁参照のクローンに標準語テキスト(「〜じゃん」「〜でしょ」)を渡すと、関西弁の抑揚グセで標準語を喋る不気味なハイブリッドになり「めっちゃ変」と評価された。参照はプロソディの方言まで固定する。標準語で作りたければ標準語話者の参照でクローンを作り直す。逆も同様
- 再現したい抑揚パターン(疑問の上昇・感嘆の跳ね上げ→急落・囁き等)を**含む区間**を選んで参照にする
- 品質基準: HNR 15dB以上(Praat `to_harmonicity_cc` で実測。8dB台=残響/ノイズあり、クローンに響きが焼き付く)。2秒窓でHNRを時系列プロファイルし、クリーンな窓だけ切り出す
- 長さ10〜30秒。ノイズ除去はAdobe Podcast Enhance(要ログイン・ブラウザ)が最良、ローカル代替はDeepFilterNet(`pip install deepfilternet soundfile` → `deepFilter --pf`)。BGMがあるならまずDemucsで分離
- **プロソディバンク方式**: 「興奮区間だけの参照」「落ち着き区間だけの参照」で別モデルを複数作り、台本の行ごとに使い分ける

### 4. 閉ループ候補選別(耳で選ばない・最重要の一般化)
生成は確率的。「聴いて→直して」はランダムウォーク。代わりに:

1. 元音声を `deep_analyze.py` で解析し、各セグメントの**数値目標**を得る(語尾スロープ・話速・F0レンジ・arousal)
2. 各行を同一リクエストで**K回(3〜5回)生成**
3. 各候補をparselmouthで計測: 最終0.15〜0.25秒のF0スロープ、全体の話速(文字数/秒)、F0平均・レンジ
4. 元音声の目標値とのL2距離が最小の候補を**機械的に採用**
5. 全候補が閾値外の行だけ、タグ/表記を変えて再generate

語尾の評価では「セグメント全体のスロープ」と「最終モーラのスロープ」を区別すること。実測した関西弁の感嘆は「フレーズ全体は上昇、**最後の一拍だけ-1000〜-3000Hz/sの急落**」という2段構造で、全体スロープだけ見ると"尻上がり"に誤読する。

### 5. ポスト編集(最後の手段)
PraatのManipulation(PSOLA)で生成音声の語尾F0だけ元音声の輪郭に変形できる。アーティファクトのリスクがあるため、閉ループで合わなかった行に限定し、処理後にHNR再計測で品質確認する。

**警告(2026-07-02実測)**: 別話者のアクセント輪郭をそのままPSOLA移植したところ、**HNRは無劣化(9.7→9.8dB)なのに聴感は「まじでダメすぎ」と即棄却**された。数値が良くても知覚品質は別物 — PSOLAでの輪郭移植は「同一話者の輪郭を微調整する」用途に留め、話者をまたぐ形状移植はしない。アクセント不良は候補サンプリング数を増やして拾う方が結果が良い(23候補中の上位が採用された)。

### 5.5 誤読・アクセント不良への対処(数字・固有名詞)
- **誤読(音素レベル)**: Whisperで候補を聞き取り検証してゲートする。ただし**Whisperは「6.5」等に正規化して書き起こすため、読み方(ろくてんご/ろくばんご等)の違いを隠す**。ゲートの正規表現は誤読パターン(「6番5」等)を明示的に弾く形にする
- **アクセント不良(ピッチパターン)**: Whisperでは検出不可。元音声に同じフレーズがあるなら、単語タイムスタンプで**当該スパンだけを切り出し、半音正規化F0輪郭の相関**でランク付けする(行全体の相関では数モーラの不良は薄まって検出できない)。候補を20個以上に増やしてサンプリングで当てるのが現実解
- ひらがな表記の強制(「ろくてんご」)は音素の誤読には効くが、アクセントまでは制御できない

### 6. ツール昇格
タグ+参照+選別でも足りない場合:
- **GPT-SoVITS / Style-Bert-VITS2 (JP-Extra)**: ローカル微調整で話者の抑揚癖自体を学習させる。SBV2は日本語イントネーションにネイティブ対応
- **RVC等のボイスチェンジャー(VC)**: 「正しい抑揚で喋った音声(自分で演じる or 別TTS)」に声質だけ乗せ替える。**プロソディと声質の完全分離**ができ、再現度は最も高い

## 最終的に勝った構成(2026-07-02実戦の結論)

8バージョンの試行の末、ユーザー評価「めっちゃいい」に到達した構成:

1. **タグはほぼ全廃**(15行中3行のみ、`[shouting]`や`[low quiet voice]`等の最小限)。カテゴリカルな感情タグ(`[scoffing]``[triumphant]``[confiding]`等)は「元にない演技の切り替え」を注入して不自然さの源になっていた。**クローン参照が既に話し方を持っているので、タグは足すな、任せろ**
2. **表記プロソディが主役**: 「!」「!?」「っ。」「。」で語尾を制御
3. **行間ギャップは元音声の実測に合わせる**: 元は中央値0.00秒の畳みかけ(捲し立て型UGC)。均一0.18秒ギャップは「紙芝居感」の主因だった。元にあった間(2箇所)だけ再現
4. **閉ループ選別の目標に「行ごとの元F0平均」を含める**: 元音声には「終盤で声が低いレジスターに沈む」大域的な弧があり(376→224→177Hz)、行単位の語尾・尺だけ合わせても弧が消えると不自然。F0目標+語尾スロープ+尺+レンジ広い方優先、の複合スコアで選別
5. **逆QA(生成物を元と同じ計測で突き合わせ)で系統誤差を発見する**: 「なんか変」の正体は (a)ギャップ構造 (b)F0が全体+58Hz高い (c)ピッチレンジが-100Hz圧縮、という3つの測定可能なズレだった。耳の違和感は必ず数値化できる

## VOICEVOX固有の知見(2026-07-03実戦: みんかちTikTok風動画ナレーション)

Fish Audioのクローンとは別に、**無料エンジンVOICEVOXで参考動画の感情曲線を転写する**場合の知見。

### 話速はデフォルトのままだと参考動画より遅くなる(実測)
VOICEVOXの`speedScale`をemotion(arousal/tension)由来の値だけ(baseline 1.0前後、0.92〜1.12の範囲)で運用すると、**参考動画実測の字/秒より体感で遅い**とユーザー指摘あり。実測で検証:
- 参考動画(ch1npan系)のコーパス平均: **6.98字/秒**
- emotion-onlyのspeedScale(base=1.0)で合成した結果: **5.81字/秒**(17%遅い)
- **`speedScale`のbaseを1.0→1.20に底上げ**(`speed = clip(1.20 + arousal*0.05 + tension*0.01, 1.05, 1.40)`)して**6.79字/秒**まで是正、体感に近づいた

**教訓**: 感情マッピングの相対的な緩急(arousal/tensionによる加減速)だけでなく、**エンジンのベース話速そのものが参考動画の実測字/秒と一致しているか毎回チェックする**。感情の起伏だけ再現してベース速度を確認しないと「抑揚はあるが全体的にもっさりした」ナレーションになる。

### 文末ピッチのテーパー処理(語尾の違和感対策)
文中の`。`/`！`直前の最終アクセント句について、`audio_query`のmorasの最後(-1)を`-0.11`、最後から2番目(-2)を`-0.05`(log-pitch単位)追加で下げると、参考動画のような「はっきり落ちる語尾」に近づく。intonationScale/pitchScaleの調整だけでは語尾の下降幅(実測90〜150Hz)を再現できない(intonationScaleの影響は数値シミュレーションで±0.02〜0.03log程度しかなく無視できるほど小さい)。

### 文単位分割合成+文末ごとの無音固定に注意
1ビートのテキストを`。`/`！`で分割して個別`audio_query`→`synthesis`し、文間に固定の無音(0.35秒目安)を挟んで結合する方式は、文ごとにピッチ/速度パラメータを独立制御できて良い。**ただし文数が多いビートで窓(尺の上限)を超えた場合、speedScaleを上げても固定無音は縮まないため頭打ちになる**。窓超過時は「speedScale上限(実用上限は1.4〜1.5、それ以上はVOICEVOXの音質が明確に劣化する)」と「文間無音を段階的に短縮(0.35→0.27→0.19→0.06秒)」を交互に試すリトライループが有効。

### カット割り動画の尺は「理論値」でなく「実測ナレーション尺+バッファ」で決める(2026-07-04追記)
文字数比例カデンス等で事前計算した各カットの尺(理論値)をそのまま動画側の表示時間に使うと、**VOICEVOXの実際の発話がその理論値より早く終わることが多く、カットごとに1〜3秒の無音("間延び")が残る**(10ビート構成の動画で合計15秒以上の無駄が生じた実例あり)。
正しい順序: ①先に全ビートをVOICEVOXで合成 ②各ビートの実際の発話尺を計測 ③実測尺+短いバッファ(通常0.3秒、CTA/オチ等の最後に画像を見せたいビートだけ0.6〜0.7秒)を新しいカット時刻として動画側に渡す ④その新カット尺で動画を再レンダリングし、ナレーションも同じ新タイミングでadelay配置する。理論値のカットは「合成前の見積もり」以上の意味を持たせない。

### ナレーションの話者を2種以上使い分けると聞き分けやすい
地の文(ナレーター)と、引用/口上/他人のコメント部分を**別のVOICEVOX話者に割り当てる**と、聞いていて誰の発言か直感的に分かりやすくなる(実例: 地の文=四国めたんツンツン、引用ナレーション部分=青山龍星)。話者名は`GET /speakers`で確認できる。ユーザーが特定の話者名(呼び方が正式名と多少違う場合がある。例: 「青山隆星」→実際は「青山龍星」)を指定してきたら、まず`/speakers`エンドポイントで名前を突き合わせてから実装する。

### BGM音量は勘で決めず`volumedetect`で実測してから逆算する
「BGMを控えめに」という指示だけで係数(例: `volume=0.22`)を決め打ちすると、曲によって音圧(マスタリングレベル)が全然違うため**曲を差し替えた途端ナレーションが聞こえなくなる**、という事故が起きた(実測: BGM単体mean_volume -18.4dB、ナレーション単体-36.6dBで18dBもの差があったのに、22%の音量係数だけでは埋まらずBGMが勝っていた)。
正しい手順:
1. `ffmpeg -i bgm.mp3 -af volumedetect -f null -` でBGM単体のmean_volumeを測る
2. `ffmpeg -i narration.mp4 -af volumedetect -f null -` でナレーション単体のmean_volumeを測る
3. 目標(BGMをナレーションの-8〜-10dB程度下にしたい)から必要な追加減衰dBを計算し、`10^(dB/20)`で線形の`volume=`係数に変換する
4. ユーザー試聴後の微調整は「BGMをもう少し下げる/ナレーションを少し上げる」の相対フィードバックが来るので、都度この計算に立ち返って係数を更新する(耳の印象だけでなく実測値ベースで追う)

### スタイル比較(ノーマル/ツンツン/あまあま/セクシー)
文末0.4秒のピッチ下降幅を実測してスタイルを選ぶ。ノーマル・ツンツンは共に-60〜-110Hz程度の自然な下降を示し参考動画の傾向(-90〜-150Hz)に近いが、あまあま・セクシーは上昇/揺れが混在し合わない。**「もっと感情的に」だからと安易にスタイル変更するより先に、この実測比較を先にやる**(スタイルより先に速度/語尾テーパーの方が効くことが多かった)。

## デバッグの型
- タグが効いていない疑い → 同一テキストで極端タグ2種のA/Bテスト(`[shouting][very excited]` vs `[whispering][monotone]`)を先に行い、効いている/いないを切り分けてから調整する
- 「クローンだからタグが効かない」と決めつけない(実測ではクローンモデルでもA/Bは明確に分離した)
- 生成物のバージョンはすべて別名で保存し、ユーザーがA/B比較できるようにする(v1, v2, ...と付番。上書き禁止)
