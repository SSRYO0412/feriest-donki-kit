# 映像管理DB 契約書（ledger-db-contract）

> 正本: `~/.claude/skills/_video-core/revision/references/ledger-db-contract.md`（sync_core.sh で配布）。
> 映像管理DB群の**単一規範**。スクリプト(`notion_*.py` = 台帳クライアント)とスキル(video-revision-db-workflow / 各案件スキル)の両方がこれを引用する。
> 設計原則: **「テキストキーが書き込みAPI、relationは派生物、スクリプトがコンパイラ、納品ゲートが強制機構」**
> （根拠: 案件V実運用でrelationが全DB・全行で100%省略された実測。エージェントに手間のかかる書き込みを義務づける規約は守られない。）

## 0. 置き場所と触り方（★2026-08-12 改定・Notion から VOPS Ledger へ）

**映像管理DBの置き場所は VOPS Ledger**（Cloudflare Workers + D1）。Notion ではない。
★**Notion には機能を1つも残さない**（2026-08-12 確定）。参考動画1秒分析シートと修正記録DBも台帳へ移し、
承認シートは機能ごと廃止した。**唯一の例外は「過去の Notion 案件を読むこと」**だけで、
書き込み・新規運用は台帳のみ（§9 の移管記録を参照）。
**運用（キー・語彙・書式・監査・ゲート）は一切変えていない。触り方だけが変わった。**

| | |
|---|---|
| 保管場所 | `https://vops-ledger.<your-org>.workers.dev`（会社スコープ・全版保持） |
| Claude Code から | **MCP が第一手段**（下表）。Notion MCP は使わない |
| 人が書き込む口 | ブラウザUI `https://vops-ledger.<your-org>.workers.dev/`（会社ID＋ページパスワード） |
| CLI | `vops ledger query|get|upsert|history|schema|flush|link` |
| スクリプトから | `core/revision/scripts/vops_ledger.py`。既存 `notion_*.py` の第1引数に **`vops:<project_id>`** を渡すだけで台帳に向く |

### 0.1 MCP ツール（これだけ覚えれば全操作が通る）

| ツール | 用途 | 必須引数 |
|---|---|---|
| `ledger_query` | 行を引く（`where`=`[{key,op,value}]` op=eq/ne/in/contains/gte/lte/is_empty、`video_id`で動画を絞る） | `project_id` `db_key` |
| `ledger_get` | 1行を取る（`version` 省略で最新、指定で過去版） | `project_id` `db_key` `record_id` |
| `ledger_upsert` | 行を作る/更新する。**送った列だけ**更新され他は消えない。更新は新版として積まれる | `project_id` `db_key` `record_id` `props` |
| `ledger_history` | その行の版の履歴（採用の変遷を追う） | `project_id` `db_key` `record_id` |
| `schema_list` | db_key 一覧 / 1DBの列・型・選択肢・ビュー | `project_id` |
| `schema_edit` | 列とビューを変える（`ops`: add_column / set_column / rename_column / drop_column / add_options / remove_options / reorder / set_view / drop_view / set_meta） | `db_key` `ops` |
| `schema_add_column` | 列を1本足す（`schema_edit` の簡易版） | `project_id` `db_key` `name` `type` |
| `ledger_flush` | オフライン中に溜まった書き込みを送る／滞留を見る | — |

**MCP サーバは2系統**（どちらも同じ台帳・同じデータ）:

| サーバ名 | 種別 | 会社の決まり方 | 備考 |
|---|---|---|---|
| `vops-ledger` | stdio（`core/ops/scripts/ledger_mcp.py`） | `~/.config/video-ops/ledger.json` の `company_id` | 社内用。**オフラインキュー付き**（`ledger_flush`）・`schema_add_column` あり |
| `vops-<会社>`（`vops-projects` / `vops-orgd` / `vops-projectf` / `vops-<your-org>`） | HTTP | **接続したアカウント**で決まる（`whoami` で確認できる） | 会社ごとの入口。案件を触る前に `whoami` で会社と `writable` を確認する |

- ★**着手前に `schema_list` を引く**。「どのDBがあるか」「列は何か」は台帳が正で、この文書は説明である。
  食い違ったら台帳が勝つ（この文書を直す）。
- ★**Notion 検索で既存DBを探す手順は廃止**。`schema_list` が既存確認そのもの。
  重複DBを作るという事故（2026-07-30）は、db_key が一意である以上、構造的に起こらなくなった。
- **既存の Notion 案件（案件V 等、Notion側に現データがあるもの）は据え置き**。移行しない。
  新規案件のみ台帳で始める。旧案件を読むときだけ Notion を見る。

### 0.2 標準の17DB と db_key（これが唯一の識別子。`collection://…` は使わない）

★**DBの数は固定ではない**（§0.3）。下表は**どの案件にも要る標準セット**で、案件に必要な表が
ここに無ければ `create_db` で増やしてよい。

| db_key | 名前 | scope | 役割 |
|---|---|---|---|

| `video_ledger` | 映像管理_動画台帳 | project | 納品物レジストリ。採用MP4/py/最終v・**過去修正メモ(=§5履歴)** |
| `asset_db` | 映像管理_素材DB | project | 編集制約台帳。1素材×時間窓=1行（§7） |
| `cut_ledger` | 映像管理_カット台帳 | **per-video** | cut_key のレジストリ。編集後の制作記録 |
| `asset_use_db` | 映像管理_素材使用DB | project | どの素材がどの動画/カットに出るか |
| `revision_request_db` | 映像管理_修正指示DB | project | 横断・方針レベルの指示の受付 |
| `render_db` | 映像管理_レンダーpy管理DB | project | **版履歴の正本**。1レンダー=1行（却下版も） |
| `qa_log_db` | 映像管理_QAログDB | project | 検品の結果と証跡 |
| `schedule_db` | 映像管理_工程・スケジュールDB | **per-video** | 工程[0]〜[9]と停止点 |
| `telop_check_db` | 映像管理_テロップチェックDB | **per-video** | 1行=1ナレーション行（字/秒・RMS） |
| `transcript_db` | 映像管理_文字起こしDB | **per-video** | ★1行=1セリフ。**全文をそのまま入れる**。AI一次判定→人が確定 |
| `script_db` | 映像管理_台本DB | **per-video** | 1行=1台本行。編集前の上流 |
| `revision_ledger` | 映像管理_修正台帳 | **per-video** | ★**案件で最も重要な成果物**。1カット=1行（`REVISION-LEDGER.md`） |
| `project_rules_db` | 案件ルール・つまずきDB | project | ★**案件の正本**。ルール（こうやる）とつまずき（こうなった）を `種別` で1つに持つ |

`scope: per-video` は**1DBの中で `video_id` で分かれる**。動画ごとに別DBは作らない（§10-2）。

### 0.3 ★DBは必要なら増やす（2026-08-12 方針変更）

以前は「db_key は固定・増やさない」としていたが、**実務では案件固有の表が要る**
（実例: 「発話3列比較（素材/完パケ/自社v10）」1873行、「ソータ テロップ台帳」106行）。
既存DBに無理に寄せると意味が壊れるので、**増やしてよい**ことにした。

```
schema_edit(db_key="utterance_compare_db", ops=[
  {"op":"create_db","name":"発話3列比較（素材/完パケ/自社）","title_prop":"位置","scope":"project"},
  {"op":"add_column","name":"①素材の発話","type":"text"}, ...])
```

| | |
|---|---|
| 作る場所 | **会社共通レイヤ**（`project_id` を付けても、DB自体は会社共通に作られる）。案件ごとの列の差分は従来どおり `project_id` 付きの ops |
| 使えるまで | **作った直後から書ける**（seed 不要・実測） |
| 冪等 | 同じ `create_db` の再実行は既存を**上書きしない**（名前も変わらない） |
| db_key の形 | 英小文字で始まる英数字と `_` のみ（2〜49文字）。合成ID `vops:{project}:{db_key}` の一要素になるため |
| `scope: per-video` | `video_id` 列が自動で付く（無いと動画ごとに分けられない） |
| UI | サーバーの一覧に載ったDBは**自動でサイドバーに出る**（scope で「案件」「動画ごと」へ振り分け） |

★**増やす前に、既存で足りないかを考える。** `revision_request_db` で足りるものを新DBにすると、
監査・ゲート・リンカーの対象から外れて「記録はあるが誰も見ない表」になる。
**判断の基準**: 既存DBの意味を歪めずに入るなら既存へ、歪むなら増やす。

★**標準17DBは減らさない・改名しない**（§8の監査・納品ゲート・リンカーがキーで結合しているため）。
増やしたDBは監査・ゲートの対象外なので、**納品の可否に関わる記録は標準DBへ書く**。

## 1. キー文法（全DBを貫く結合キー）

| キー | 正規表現 | 例 | レジストリ(定義元) |
|---|---|---|---|
| `video_id` | `\d{3,4}(_\d{2})?` | `0290`, `0181_05` | `video_ledger` |
| `render_key` | `<video_id>_v<NN>(_<variant>)?` = `\d{3,4}(_\d{2})?_v\d+(_[A-Za-z][\w]*)?` | `0290_v32`, `0287_v9_B` | `render_db` |
| `cut_key` | `<video_id>_c<NN>` | `0181_05_c03` | `cut_ledger` |

- バリアント記号: `A`=顔あり, `B`=顔なし を既定とし、案件で追加定義可（契約に追記）。
- `check_adoption_sync.py` の adopted.json では video_id をバリアント込み `0290_B` 形式で使う。
- キーは**行作成時にエージェントが必ず書く**（手元にある文字列なので省略の動機がない）。
- ★**`record_id` にもキーを使う**（`ledger_upsert` の `record_id`）。`render_db` なら `render_key`、
  `cut_ledger`/`revision_ledger` なら `cut_key`、`video_ledger` なら `video_id`。
  こうしておくと同じ行への更新が自然に冪等になり、`ledger_history` がその行の変遷になる。

## 2. 書き込み契約（Write Contract）

| 書き手 | 書くもの |
|---|---|
| **エージェント(必須)** | テキストキー(`video_id`/`render_key`/`cut_key`)、構造化フィールド(ステータス・採用状態・却下理由・根拠・パス・数値)、指示への対応メモ |
| **エージェント(条件付き)** | relation直書きは「対象の `record_id` が既にコンテキストにある場合のみ」(例: 台帳行を読んだ直後にレンダー行を作る時)。**IDを調べに行ってまで張らない** |
| **スクリプトのみ(手打ち禁止列)** | relation一括(autolink)、`video_ledger` の`採用サマリ`/`最終v`/`採用MP4パス`/`採用pyパス`(=レンダー行から生成する鏡)、`整合`、`納品ゲート結果`、VERSIONING§5書式の履歴行 |
| **台帳が自動** | `最終更新`(=現行版の作成時刻)、`version`(版番号。`ledger_history` で見る) |

**採用の変更**はエージェントの2操作のみ:
1. `render_db` の該当行 `採用状態` をフリップ（新採用行→`採用`、旧採用行→`旧採用`）
2. `video_ledger` の `採用レンダー` relation を差し替え（レンダー行の `record_id` は手元にあるはず）
→ §5履歴文・採用サマリ・鏡列はリンカーが生成する。

★**`props` は差分パッチ**。`ledger_upsert` には**変えた列だけ**を入れる。全列を送り直す必要はないし、
送らなかった列が消えることもない（サーバー側でマージされる）。

## 3. DB別プロパティ台帳（正規 / 非推奨 / 派生）

凡例: ★=キー(エージェント必須) / ◆=派生(手打ち禁止・スクリプトが書く) / (旧)=非推奨(旧_プレフィックス、読み取り専用)

### `video_ledger` 動画台帳（=納品物レジストリ。採用の「中身」は `render_db` が正本）
- ★`video_id`(text) / 動画名(title) / 動画番号(text) / ステータス(select: 制作中/修正中/納品済み/アーカイブ)
- `採用レンダー`(relation→`render_db`, multi。バリアントごとに1本) — エージェント(採用確定時)+リンカー補完
- ◆`採用サマリ`(text: `A(顔あり): v32 <mp4path>` 形式でリンカー生成) / ◆`最終v` / ◆`採用MP4パス` / ◆`採用pyパス` / ◆`整合`(select: OK/不整合/未リンク)
- ◆`過去修正メモ`(text) — ★**§5 の人間可読な履歴はここに追記する**（Notion時代のページ本文の置き換え）。
  台帳にページ本文は無い。**追記は read-modify-write**（`ledger_get` で現在値を読み、末尾に足して `ledger_upsert`）。
  **消して書き直さない**。生成は `notion_autolink.py --apply` が行う
- `最終更新`(自動) / 残課題(text) / 納品フォルダ(path)

### `render_db` レンダーpy管理DB（=**バージョン履歴の正本**。1レンダー=1行、却下版も必ず行にする）
- ★`render_key`(text・`record_id` にも使う) / ★`video_id`(text) / `v`(number) / `バリアント`(select: なし/A_顔あり/B_顔なし)
- `採用状態`(select: **採用/却下/旧採用/未判定**) / `却下理由`(text) / `根拠`(text: 48分割目視・尺実測・クライアント承認 等) / `判定日`(date)
- `pyパス`(path, フルパス必須) / `MP4パス`(path) / `中間素材パス`(path) / 音声ソース(text) / BGMソース(text) / 出力日時(date)
- relation: `動画`(→`video_ledger`) / `修正指示`(→`revision_request_db`) — キーからリンカーが張る

### `revision_request_db` 修正指示DB
- 指示タイトル(title) / ★`対象video_id`(text, カンマ区切り可) / `全動画対象`(checkbox)
- ステータス(select: 新規/確認中/設計済み/作業中/レンダー済み/検品中/修正完了/納品済み/却下/保留)
- 修正種別(multi) / 優先度(select) / 対象cut id(text, cut_key文法) / 対象秒数(text, §6書式) / 指示内容 / 対応方針 / 対応後メモ / 検品結果 / 受付日 / 完了日
- relation: 動画(リンカー)
- (旧)`旧_関連py`/(旧)`旧_関連レンダー` → `render_db` 側 relation の逆参照で代替

### `qa_log_db` QAログDB
- QA名(title) / ★`video_id`(text) / ★`render_key`(text) / QA種別(multi) / `結果`(select: OK/NG/条件付きOK) / 確認内容 / 対象秒数(§6書式) / 証跡パス(qa/配下) / 確認日
- 3軸/突合の数値列: `軸1_最低スロット点` / `軸2_FidelityIndex` / `軸2_肝遵守` / `軸2_盲検AB識別率` / `軸3_ゲート違反数` / `軸3_Codex評点` / `突合ゲート結果`
- relation: 動画/修正指示/レンダー(リンカー)

### `cut_ledger` カット台帳（=cut_keyのレジストリ。制作記録・per-video）
- ★`cut_key`(text) / ★`video_id`(text) / カット名(title) / `動画開始秒`・`動画終了秒`・`尺`(number) / `台本/テロップ` / `素材tin`(number) / `意図` / `顔/クロップ方針`
- relation: 動画/素材(リンカー)
- **編集後の記録**。修正指示の受付は下記の修正台帳が担う（役割を混ぜない）

### ★`revision_ledger` 修正台帳（=修正指示の受付窓口。**案件で最も重要な成果物**・per-video）
- **1カット=1行**。`video_id` で動画ごとに分かれる。設計・作成・運用の正本は `REVISION-LEDGER.md`
- **必須4列**（欠けると運用が成立しない）:
  **`修正指示`**(text ←人が書く) / **`採否`**(select: 採用/修正/DROP/HOLD ←人が選ぶ) /
  `テロップ文言`(text=どの絵かを言葉で特定) / `動画内開始秒`(number=並び順の根拠)
- キー: ★`cut_key`(`record_id` にも使う) / ★`video_id` / `cut id` / `カット名`(title) / `動画内終了秒` / `尺`
- 内容: `台本/VO文言` / `コンテカテゴリ` / `使用意図`
- 進捗・履歴: `ステータス`(select: 未確認/確認済み/要修正/対応中/修正済み/却下) / `初回採否`(select) /
  `変更区分`(select: 新規/差し替え/追加採用/採用取消/置かないへ変更/修正指定/修正から復帰/再DROP) /
  `変更履歴`(追記のみ `YYYY-MM-DD 旧→新(理由)`) / `DROP理由` / `却下理由` / `修正日`(date) / `選定版`
- 素材と画: `使用素材名` / `素材内開始秒 tin`・`素材内終了秒 tout`(number) / `スケール`(number) /
  `モーション` / `人物判定`(demo/pass/edge/none) / `クロップ指定` / `顔あり/顔なし指定`(select) /
  `BGM/SEメモ` / `注意事項`
- ★**DROP は `ステータス` では表せない**（「このカットを使わない」）。`採否` を省略しない
- 案件で使わない列は**ビューから外すだけ**（消さない。`schema_edit` の `set_view`）

### `asset_use_db` 素材使用DB
- ★`cut_key`(text) / ★`video_id`(text) / 使用名(title) / 使用意図 / 台本との関係 / `注意/禁止` / 動画秒数 / 素材秒数
- relation: 動画/カット/素材(リンカー)

### `asset_db` 素材DB（=**編集制約台帳**。1素材×時間窓=1行。§7参照）
- 素材名(title) / `素材rel`(text: カタログと共有のキー) / `素材パス`(path) / 種類 / 顔ルール / `音声/BGM状態` / `使いやすい秒数` / `使ってはいけない秒数` / `verdict要約`(text: verified_clips.jsonから転記)
- 窓の列: `t0秒` / `t1秒` / `verdict` / `使用条件` / `判定理由` / `確定者` / `clip_kind` / `sim_cluster` / `カタログ正本パス`
- ★**confirmed_by が付いた窓のみ転記**（AI提案は転記しない）

### `telop_check_db` テロップチェックDB（per-video）
- 行テキスト(title) / ★`video_id`(text) / `行No`(number) / `cut id`(text, cut_key文法) / `文字数(スペース除く)`(number) / `表示秒数`(number) / `字/秒`(number) / `音量RMS実測(dB)`(number) / フラグ(multi) / ステータス(select: 未確認/修正対象/修正中/修正済み/承認済み) / 元py / 採用v / 修正メモ / 最終更新(自動)
- relation: 動画(リンカー)

### `transcript_db` 文字起こしDB（=素材の全発話。per-video）
1行=1セリフ。**密着・インタビュー系では数千行になる**（実例: D社チャンネル 1713行）。

- `行ID`(title) / ★`video_id`（**完成動画**） / ★`素材ID`（**撮影ファイル**） / `開始秒`・`終了秒`・`尺`(number)

★**階層は3段（案件 → 動画 → 素材 → 行）**。密着・インタビューは1本の動画が複数の撮影ファイル
からできており、**1つの表に混ぜると開始秒が入り乱れて時系列が読めない**（2026-08-12 ユーザー指摘で修正）。
スキーマの `sub_key` が2段目のキー名を持ち（`transcript_db` は `素材ID`）、UI は
「動画のカード → 素材のカード → 行」と降りる。素材カードには行数と開始秒を出す。

- `話者`(select・**選んで直せる**) / `話者確信度`(number) / `発話`(text) / `元ファイルパス`
- **AIの一次判定**: `AI採否`(select: 採用/非採用/保留/未判定) / `AI理由` / `AI確信度`(number)
- **人の確定**: `採否`(select: **未確認**/採用/非採用/保留) / `判定者` / `判定日` / `メモ` / `使用先cut_key`

★**仕様（違反厳禁）**
1. **最初に全文を入れ切る。選定してから入れない。** 入れる時点で捨てた行は二度と検討されず、
   「あの発言どこだっけ」が探せなくなる。採否は空ではなく **`未確認`** から始める
   （空だと「まだ見ていない」と「見たうえで保留」が区別できない）
2. **AIの判定と人の判定は別列**。AIが `AI採否` を埋め、人は `採否` を触る。
   **AIが人の列を上書きしない**（上書きすると人の判断が消え、しかも消えたことが分からない）
3. `話者` と `採否` は **select（選択）**。ASRの話者推定は外れるので、人が選び直す前提

**タブ（ビュー）**: `★全文（0秒から）` / `AIが採用` / `★人が未確認` / `確定（採用）` /
`AIと人が食い違う`（**両方向**: AI非採用×人採用 と AI採用×人非採用） / `全列`。
UI はビューをタブで出し、**件数も表示する**（どこまで見たかが分かる）。

★**ビューは会社共通に置く。** 案件レイヤでビューを設定すると、その案件だけ会社の変更が
届かなくなる（サーバーは「ビューを触った ops のときだけ」案件レイヤに焼く。2026-08-12 修正済み）。

`script_db` との違い: `transcript_db` は**素材に何が入っているか**（全発話）、
`script_db` は**そこから組んだ台本**（採用行の並び）。前者から後者を作る。

### `skill_db` 関連スキルDB（=この案件で使うスキル。★本文ごと持つ）
- スキル名(title) / `ファイルパス` / `GitHubリンク`(url) / `使い方`(text) / `最終更新日`(date)
- ★本文用: `本文`(text) / `取得コミット`(blob SHA 7桁) / `取得日時`(date) / `バイト数`(number)

★**1ファイル=1行で本文ごと載せる**（2026-08-13）。理由は、スキルのリポジトリが private で、
**クライアントや外注は GitHub を持っていない**から。リンクだけでは彼らに何も届かない。

| | |
|---|---|
| 正本 | **リポジトリ**。台帳は**キャッシュ**（古くなり得る） |
| 古さの検出 | `取得コミット`(blob SHA) を GitHub の現在値と突き合わせる → `skill_sync check` |
| ★GitHubが無い人 | `skill_sync install --dest ~/.claude/skills` で**台帳から復元して使える** |
| 載せるもの | テキストのみ（.md/.py/.json/.jsx/.sh ほか）。バイナリは載せず、報告する |
| 上限 | 1行 240KB（サーバーは256KB）／1リクエスト 700KB（同1MB）。バイト数でバッチを切る |
| `使い方` | **push で上書きしない**（人が書いた文章を機械が消さない） |

```
skill_sync.py push    --project-id <案件> --skill <名前> --repo <owner/name> [--subdir <path>]
skill_sync.py check   --project-id <案件>      # 台帳のSHA vs GitHub。古い行を名指しする
skill_sync.py install --project-id <案件> --dest ~/.claude/skills   # ★GitHub不要
```

**実測（2026-08-13・DEH/project_d）**: 4スキル62ファイル（396KB）を投入し、`install` で
書き出したものを GitHub 原本と**全数バイト比較して62/62一致**。`check` は62件すべて最新と判定。
同じ tag での再 push は版が増えない（冪等）。
- **何のためか**: 案件を引き継いだ人・次のセッションが「この案件はどのスキルで回すのか」を
  1箇所で分かるようにする。CLAUDE.md や記憶に散らすと、読まれずに素通りする
- `使い方`は**この案件での使いどころ**を書く（スキルの説明文の写しではない）
- `最終更新日`は**スキル側を直した日**。直したら更新する（古い版を前提に作業する事故を防ぐ）
- 既定ビュー `★最終更新が新しい順`

### `project_rules_db` 案件ルール・つまずきDB（=★案件の正本。引き継ぎの本体）
**担当・セッション・マシンが変わっても、ここを読めば案件を再現できる**ことを目的にした唯一のDB。

- ルール本文(title) / `rule_key` / **`種別`(select: ルール/つまずき)** / **`重要度`(select: ★毎回読む/通常)** /
  工程(select: カット選定/テロップ/音声/検品/素材/納品/その他) / 理由 / 出典（ユーザー指摘は**原文引用**） / 追加日 / 状態(有効/廃止)
- つまずき用: `事象`（何が起きたか） / `真因` / `再発防止`（次はこうする・強制機構） / `再発回数` / `関連`(video_id・cut_key・パス)
- ★**正本は台帳**（2026-08-13 改定。以前はローカル `rules.jsonl` が正本だった）。
  ローカルの `rules.jsonl` と `<案件>/.claude/skills/<案件名>-rules/SKILL.md` は **`rules.py pull` が作る生成物**。
  理由: 案件フォルダや個人の memory に置くと、**引き継いだ瞬間に消える**（実際に起きている）
- ★**1DBに種別で持つ**。ルールとつまずきを別DBにしない（書く動機は違うが、読むのは同じ場面）
- ★**廃止しても行は残す**（`状態=廃止`）。「なぜ止めたか」も資産

**運用**:
```
rules.py add --process カット選定 --rule "..." --reason "..." --source "YYYY-MM-DD ユーザー『原文』"
rules.py add --type つまずき --process 音声 --important --rule "次はこうする" \
             --event "何が起きた" --cause "真因" --fix "再発防止"
rules.py pull            # 台帳 → キャッシュ + 案件スキル再生成
rules.py brief           # SessionStart に流し込む本文
```

**読ませ方（2026-08-13 確定）**: 案件の SessionStart hook が `rules.py brief` を実行し、
**恒久ルールは全文・★のつまずきは全文・残りのつまずきは見出しで全件**をコンテキストへ入れる。
台帳が引けなければキャッシュへ退避し、**セッションは止めない**（8秒で打ち切る）。

**書かせ方（同日）**: Stop hook（`session_end.sh`）が、そのセッションで1件も増えていなければ
**1回だけ停止して問う**（2回目は必ず通す＝無限ループにしない）。「後でまとめて」は必ず忘れるため。

**既存案件への後付け**: `wire_project.py --project <案件ルート> --project-id <id>` が
project.json の `ledger` 節・`.claude/settings.json`（SessionStart / Stop / PreToolUse）・
案件ルートの台帳登録・`rules.py pull` を冪等に行う。
★`fork_project.py` で作っていない案件は hook が無いので、**この配線をしないと何も自動で入らない**。

**ビュー**: `★毎回読む`（有効なルール＋★のつまずき） / `恒久ルール` / `つまずき全部` / `廃止・解決済み` / `全列`

## 5. 履歴の構造

台帳は**更新のたびに新版を積む**（上書きしない）。履歴は3層で読める。

| 層 | 実体 | 読み方 |
|---|---|---|
| 版履歴（自動・全列） | 行のバージョン | `ledger_history` / `ledger_get --version N` |
| **構造化履歴（正本）** | `render_db` の全行(v・採用状態・却下理由・根拠・判定日) | `ledger_query`。却下一覧も採用遷移もクエリで復元できる |
| **人間可読の履歴** | `video_ledger` の `過去修正メモ` へ日付付き追記（VERSIONING§5書式） | 動画1本の変遷を1セルで読む |

人間可読の履歴はリンカーがレンダー行から合成して追記する(冪等・追記のみ・消去禁止):
`YYYY-MM-DD: v<NN>採用 ← v<MM>却下(<却下理由>)。根拠=<根拠>。py=<pyパス>`

★履歴専用DBは作らない。★`ledger_history` があるからといって `過去修正メモ` を省かない
（版履歴は「何が変わったか」であって「なぜ採用が動いたか」ではない）。

## 6. 書式規約

- **秒数**: `<start>-<end>s`(例 `10.5-13.0s`) または単点 `12.5s`。語彙許可リスト: `冒頭`/`末尾`/`全体`。監査がregex検証。
- **パス**: 採用値は再生成可能なフルパスのみ。禁止パターン(監査FAIL): `pyなし`※ / `各build_*` / `詳細(py)?未確認` / `〜参照` 単体。
  ※原版コピー等でpyが本当に存在しない場合は `py不要(理由: <理由>)` の定型で書く(監査は定型のみ許可)。
- **cut id**: cut_key文法。`未確認`等のプレースホルダは監査FAIL。
- ★**パス列は `path` 型**。台帳は保存時に **NFC 正規化**し、案件ルート相対の `path_rel` を自動で併記する
  （exFATの日本語名がNFDで返る問題への対処）。**書く側は従来どおりフルパスを書けばよい**。
  案件ルートの登録は `vops ledger link <project_id> <案件ルート>`（未登録でも壊れない。`path_rel` が null になるだけ）

## 8. 監査不変条件(notion_audit.pyが実装。FAILで納品不可)

1. **(video_id, バリアント)ごとに `採用状態=採用` の行はちょうど1つ**(0=未確定WARN、2以上=FAIL)
2. キーは文法regexに一致(不一致=FAIL)
3. キーがあるのにrelation欠落 → autolink対象(自動修復)。キーが解決不能(参照先の行が無い) → FAIL
4. 採用パスは§6のパス規約に一致(非パス参照=FAIL)
5. ステータスは§4正規語彙のみ(レガシー値=WARN+変換提案)
6. レンダー行があるのに対応する修正指示が終端ステータスでない期間が続く → WARN(ステータス放置検出)
7. ローカルの全(video_id, v)に `render_db` 行が存在(check_adoption_sync[F]。却下版の未登録=FAIL)
8. cut_key孤児(`cut_ledger` に無いcut_keyを他DBが参照)=FAIL、プレースホルダ(`未確認`)=FAIL
9. `video_ledger` の◆派生列とレンダー採用行の値が一致(不一致=`整合`列に記録+FAIL)

## 9. ゲートとツール(実行タイミング)

スクリプト名は `notion_*.py` のままだが、**第1引数に `vops:<project_id>` を渡せば台帳に向く**
（`vops_ledger.py` が互換シムとして両方を吸収する。実UUIDを渡した場合だけ Notion に向く）。

| 案件をまたいで参照するもの（学び・判断文法） | 数百行規模のカタログ全量（403行投入は2026-07-27にユーザー判断で見送り済み＝正しい判断） |

### ★スキーマは固定ではない（案件ごとに毎回変えてよい）
**`ledger-db-schema.json` は「新規案件の初期値」**。実際の案件では列も選択肢も毎回変わる前提。

| どこを変えるか | 指定 |
|---|---|
| その案件だけ | `schema_edit` に `project_id` を付ける（他案件・新規案件に影響しない） |
| 新規案件の初期値（会社共通） | `project_id` を省く（既存案件は自分の差分を持つので動かない） |

- ★**列を消してもデータは消えない**（表示から外れるだけ。再追加すれば見える）
- ★**改名は中身のキーも書き換える**（`rename_column`。`renamed_rows` に件数が返る）
- ★**スキーマに無いキーへの書き込みは拒否されない**が未定義キーとして記録される。
  `GET /v1/schema/undefined?db_key=...` で棚卸しする（`撮影日` と `撮影日時` が両方できる沼を避けるため）
- テンプレ更新は既存案件に自動反映されない。**差分適用**する（`schema_edit` で列追加＋適用日を `project_ledger.備考` に記録）

## §10 ★時系列表示と複数本運用（2026-07-30制定・違反厳禁。台帳版に読み替え）

### §10-1 時系列は必須。設定して、さらに実際に引いて検証する
**時間軸を持つDBは、投入したら必ず「0秒から最後まで時系列に流れる」ビューを設定する。**
ユーザーから**3回**指摘された（承認シート〈廃止〉/1秒分析シート/台本DB）。設定漏れは工程スキップと同じ扱い。

| db_key | 主ソート | グループ | 既定ビュー名 |
|---|---|---|---|
| `script_db` | **`開始秒` ASC** | `video_id` | ★本編の時系列（0秒から・記入用） |
| `schedule_db` | `順序` ASC | `video_id` | ★工程順（動画別） |
| `cut_ledger` | `動画開始秒` ASC | `video_id` | ★0秒から時系列（動画別） |
| `revision_ledger` | `動画内開始秒` ASC | `video_id` | 0秒から時系列（記入用） |
| `telop_check_db` | `行No` ASC | `video_id` | ★行順（動画別・記入用） |
| `asset_db` | `素材名` ASC → `t0秒` ASC | — | |
| `revision_request_db` | `受付日` ASC | `対象video_id` | |
| `qa_log_db` / `render_db` | `確認日`/`出力日時` ASC | `video_id` | |
| `ref_sheet_db` | `開始秒` ASC | `video_id`（=参考動画） | ★0秒から時系列（参考動画別） |
| `revision_record_db` | `実行日時` DESC（新しい順） | — | ★新しい順 |

設定は `schema_edit` の `set_view`:

```
ops: [{"op":"set_view","name":"0秒から時系列（記入用）","type":"table",
       "display_properties":["カット名","動画内開始秒","テロップ文言","修正指示","採否","ステータス"],
       "sorts":[{"property":"動画内開始秒","direction":"ascending"}],
       "group_by":"video_id","first":true}]
```

- ★**`first: true` で既定ビューにする**。ビューを足すだけでは、ユーザーが最初に開くビューが時系列にならない
- ★**設定したら `ledger_query` で実際に引き、先頭が0秒・末尾が最終行であることを確認してから完了と言う**
  （申告だけで「時系列にした」と言わない）
- ★**ビューの列がスキーマから消えると UI は黙って全列表示に落ちる**（サーバーの `test/test_views.py` が検出する）
- **`script_db` のDROP行にも `開始秒` を入れる**（値=元発話のt0）。空だと採用行の後ろでバラバラに並ぶ

### §10-2 動画ごとの分離は `scope: per-video`（★2026-08-12 台帳版へ改定）

**Notion時代の原則**は「動画ごとに別ページを作り、そのページの中にDBを置く」だった（2026-08-08 ユーザー指摘。
原文:「動画ごとにDBを作らず1DBに全動画＋GROUP BY これが間違っている 正確には動画ごとに別ページでDBを作る」）。

**台帳ではこれを `scope: per-video` として実装している。** 満たすべき要件は同じで、実現手段だけが変わった。

| 要件（変えていない） | 台帳での実現 |
|---|---|
| 1つの表に複数動画の秒数を混ぜない | **まず動画を選んでから中に入る**（UIは動画カード一覧が入口／MCPは `ledger_query` の `video_id` 引数） |
| 0秒が複数現れないこと | ビューの `group_by: video_id` ＋ 秒ソート |
| 選択肢が動画/商材ごとに汚れないこと | `schema_edit` に `project_id` を付けて**案件ごとの差分**にする（会社共通を汚さない） |
| 案件をまたいで集計できること | 各行の `video_id` は**引き続き必須**（結合キー） |

- ★**動画ごとに別DBは作らない**（`video_id` で分ける）。DBを増やすのは「別の種類の表」が要るときだけ（§0.3）
- **案件 > 商材 > 動画** の階層は `project_id`（案件）と `video_id`（動画）で表す
- キー文法（§1）を守る: `video_id` / `render_key` / `cut_key` / 台本行=`行ID`＋`video_id` の組で一意
- **版が変わったら行を消さず `台本v` を上げて新規行**（旧版は残す＝履歴保全）
- 案件全体を横断して見たいときは `ledger_query`（`video_id` を指定しなければ全動画が引ける）

### §10-3 台本レビューの「修正」レーン
`script_db` は**人がレビューして行単位で修正指示を出す**器でもある。そのための4列を持つ:

| 列 | 型 | 使い方 |
|---|---|---|
| `採否` | select | **採用 / 修正 / DROP / HOLD**。人が「修正」を選ぶと修正レーンに入る |
| `修正指示` | text | **人が書く**。何をどう直すか（原文で書いてよい） |
| `修正ステータス` | select | 未対応 / 対応中 / 対応済み / 却下（エージェントが更新） |
| `修正日` | date | 対応した日 |

運用: 人が `採否=修正` ＋ `修正指示` を書く → エージェントは**その行だけ**を直し、
ローカル正本(`script.json`)を更新して `修正ステータス=対応済み` ＋ `修正日` を打つ →
`備考` に何を変えたか（【R11修正】等のタグ付き）を追記して履歴を残す。
**動画単位の修正依頼は従来どおり `revision_request_db`**（粒度が違う。台本行の修正はこの4列で完結させ、DBを増やさない）。

### §10-4 状態遷移の可視化（「後から追加した行がどこか分からない」問題の根治）
`採否` は**現在の状態**しか表さないため、後から採用に昇格した行が既存の採用行に紛れて判別不能になる。
遷移は**別列**で持つ（採否に「追加採用」を足すと時系列ソートが2グループに割れて§10-1に反するため）。

| 列 | 型 | 意味 |
|---|---|---|
| `変更区分` | select | **追加採用**(DROP/HOLD→採用) / **採用取消**(採用→DROP) / **保留化**(採用→HOLD) / **修正指定**(採用→修正) / **修正から復帰**(修正→採用) / **再DROP** |
| `変更履歴` | text | **追記のみ**。書式 `YYYY-MM-DD v<台本v>: 旧→新（理由）` |
| `初回採否` | select | 最初に確定した採否。遷移時に旧値を入れる（空欄=一度も変わっていない） |

- 遷移が起きたら**3列すべてを同時に更新**する（片方だけ書かない）
- **空欄=変更なし**なので、`ledger_query` に `where: [{"key":"変更区分","op":"is_empty"}]` の否定で
  「追加・変更された行」が全部引ける。ビューも2枚用意する:
  **★本編の時系列**（`採否 != DROP AND != HOLD` / 秒ASC）と **★追加・変更のみ**（`変更区分` が空でない）
- ★**select列の選択肢を変えた直後は必ず全行の値をクエリで検算する**。
  2026-07-30に `採否` の変更前後で**1行だけ値が DROP→採用 に化けた**（実クエリで検出・復旧）。
  スキーマ変更は既存データを壊し得るので、変更→検算→修復までを1セットで行う
  （台帳では版が積まれるので、壊した場合も `ledger_get --version N` で前の値を取り戻せる）

### §10-5 ★ユーザーの操作を「データ化け」と誤診して上書きしない（実際に起こした事故）
台帳の値が自分の記録と食い違ったとき、**最初に検討すべきは「ユーザーが操作した」可能性**である。

**起こした事故**: ユーザーが台本DBの1行を `DROP→採用`（追加採用）に変更したのを、Claudeが
「select列の変更で値が化けた」と誤診し、**ユーザーの判断を勝手にDROPへ戻した**。
さらに変更履歴に「スキーマ変更で化けた」という**誤った説明を書き込んだ**。

**恒久ルール**:
1. 自分の記録と違う値を見つけたら、**まず `ledger_history` を引く**（誰がいつ何を変えたかが版として残っている）。
   痕跡がなくても**上書きする前にユーザーに確認する**（値の復元は破壊的操作）
2. 直近に自分がスキーマ変更をしていても、それを第一の容疑者にしない
   （2026-07-30の件は、スキーマ変更とユーザー操作の時刻が偶然近かっただけ）
3. 誤って上書きした場合は、**変更履歴に誤診と撤回を明記**して復旧する（消さずに残す）
