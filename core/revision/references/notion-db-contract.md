# Notion映像管理DB 契約書（notion-db-contract）

> 正本: `~/.claude/skills/_video-core/revision/references/notion-db-contract.md`（sync_core.sh で配布）。
> 映像管理Notion DB群の**単一規範**。スクリプト(notion_*.py)とスキル(video-revision-db-workflow / 各案件スキル)の両方がこれを引用する。
> 設計原則: **「テキストキーが書き込みAPI、relationは派生物、スクリプトがコンパイラ、納品ゲートが強制機構」**
> （根拠: 案件V実運用でrelationが全DB・全行で100%省略された実測。エージェントに手間のかかる書き込みを義務づける規約は守られない。）

## 1. キー文法（全DBを貫く結合キー）

| キー | 正規表現 | 例 | レジストリ(定義元) |
|---|---|---|---|
| `video_id` | `\d{3,4}(_\d{2})?` | `0290`, `0181_05` | 動画台帳 |
| `render_key` | `<video_id>_v<NN>(_<variant>)?` = `\d{3,4}(_\d{2})?_v\d+(_[A-Za-z][\w]*)?` | `0290_v32`, `0287_v9_B` | レンダーpy管理DB |
| `cut_key` | `<video_id>_c<NN>` | `0181_05_c03` | カット台帳 |

- バリアント記号: `A`=顔あり, `B`=顔なし を既定とし、案件で追加定義可（契約に追記）。
- `check_adoption_sync.py` の adopted.json では video_id をバリアント込み `0290_B` 形式で使う。
- キーは**行作成時にエージェントが必ず書く**（手元にある文字列なので省略の動機がない）。

## 2. 書き込み契約（Write Contract）

| 書き手 | 書くもの |
|---|---|
| **エージェント(必須)** | テキストキー(`video_id`/`render_key`/`cut_key`)、構造化フィールド(ステータス・採用状態・却下理由・根拠・パス・数値)、指示への対応メモ |
| **エージェント(条件付き)** | relation直書きは「対象ページIDが既にコンテキストにある場合のみ」(例: 台帳行をfetch済みでレンダー行を作る時)。**IDを調べに行ってまで張らない** |
| **スクリプトのみ(手打ち禁止列)** | relation一括(autolink)、動画台帳の`採用サマリ`/`最終v`/`採用MP4パス`/`採用pyパス`(=レンダー行から生成する鏡)、`整合`、`納品ゲート結果`、VERSIONING§5書式の履歴行 |
| **Notion自動** | `最終更新`(last_edited_time)、unique_id |

**採用の変更**はエージェントの2操作のみ:
1. レンダーpy管理DBの該当行 `採用状態` をフリップ（新採用行→`採用`、旧採用行→`旧採用`）
2. 動画台帳の `採用レンダー` relation を差し替え（台帳行IDは手元にあるはず）
→ §5履歴文・採用サマリ・鏡列はリンカーが生成する。

## 3. DB別プロパティ台帳（正規 / 非推奨 / 派生）

凡例: ★=キー(エージェント必須) / ◆=派生(手打ち禁止・スクリプトが書く) / (旧)=非推奨(旧_プレフィックス、読み取り専用)

### 動画台帳（=納品物レジストリ。採用の「中身」はレンダーDBが正本）
- ★`video_id`(text) / 動画名(title) / 動画番号(text) / ステータス(select: 制作中/修正中/納品済み/アーカイブ)
- `採用レンダー`(relation→レンダーpy管理DB, multi。バリアントごとに1本) — エージェント(採用確定時)+リンカー補完
- ◆`採用サマリ`(text: `A(顔あり): v32 <mp4path>` 形式でリンカー生成) / ◆`最終v` / ◆`採用MP4パス` / ◆`採用pyパス` / ◆`整合`(select: OK/不整合/未リンク)
- `最終更新`(last_edited_time, 自動) / 残課題(text) / 納品フォルダ(text)
- (旧)`過去修正メモ` → 履歴はページ本文へ§5書式で追記(リンカー生成)

### レンダーpy管理DB（=**バージョン履歴の正本**。1レンダー=1行、却下版も必ず行にする）
- ★`render_key`(text) / ★`video_id`(text) / `v`(number) / `バリアント`(select: なし/A_顔あり/B_顔なし)
- `採用状態`(select: **採用/却下/旧採用/未判定**) / `却下理由`(text) / `根拠`(text: 48分割目視・尺実測・クライアント承認 等) / `判定日`(date)
- pyパス(text, フルパス必須) / MP4パス(text) / 中間素材パス(text) / 音声ソース(text) / BGMソース(text) / 出力日時(date)
- relation: 動画(→動画台帳) / 修正指示(→修正指示DB) — キーからリンカーが張る

### 修正指示DB
- 指示タイトル(title) / ★`対象video_id`(text, カンマ区切り可) / `全動画対象`(checkbox)
- ステータス(select: 新規/確認中/設計済み/作業中/レンダー済み/検品中/修正完了/納品済み/却下/保留)
- 修正種別(multi) / 優先度(select) / 対象cut id(text, cut_key文法) / 対象秒数(text, §6書式) / 指示内容 / 対応方針 / 対応後メモ / 検品結果 / 受付日 / 完了日
- relation: 動画(リンカー) 
- (旧)`関連py`/(旧)`関連レンダー`/(旧)`対象動画名`(select) → レンダーDB側relationの双方向表示で代替

### QAログDB
- QA名(title) / ★`video_id`(text) / ★`render_key`(text) / QA種別(multi) / `結果`(select: OK/NG/条件付きOK) / 確認内容 / 対象秒数(§6書式) / 証跡パス(qa/配下) / 確認日
- relation: 動画/修正指示/レンダー(リンカー)

### カット台帳（=cut_keyのレジストリ。制作記録）
- ★`cut_key`(text) / ★`video_id`(text) / カット名(title) / 開始秒・終了秒・尺(number) / テロップ文言 / 素材tin(number) / 意図 / 顔・クロップ方針
- relation: 動画/素材(リンカー)
- **編集後の記録**。修正指示の受付は下記の修正台帳が担う（役割を混ぜない）

### ★修正台帳（=修正指示の受付窓口。**案件で最も重要な成果物**）
- **1カット=1行**。動画ごとに1DB（既定）を動画ごとのページに置く。設計・作成・運用の正本は `REVISION-LEDGER.md`
- **必須4列**（欠けると運用が成立しない）:
  **`修正指示`**(text ←人が書く) / **`採否`**(select: 採用/修正/DROP/HOLD ←人が選ぶ) /
  `テロップ文言`(text=どの絵かを言葉で特定) / `動画内開始秒`(number=並び順の根拠)
- キー: ★`cut_key` / ★`video_id` / `cut id` / `カット名`(title) / `動画内終了秒` / `尺`
- 内容: `台本/VO文言` / `コンテカテゴリ` / `使用意図`
- 進捗・履歴: `ステータス`(select: 未確認/確認済み/要修正/対応中/修正済み/却下) / `初回採否`(select) /
  `変更区分`(select: 新規/差し替え/追加採用/採用取消/置かないへ変更/修正指定/修正から復帰/再DROP) /
  `変更履歴`(追記のみ `YYYY-MM-DD 旧→新(理由)`) / `DROP理由` / `却下理由` / `修正日`(date) / `選定版`
- 素材と画: `使用素材名` / `素材内開始秒 tin`・`素材内終了秒 tout`(number) / `スケール`(number) /
  `モーション` / `人物判定`(demo/pass/edge/none) / `クロップ指定` / `顔あり/顔なし指定`(select) /
  `BGM/SEメモ` / `注意事項`
- ★**DROP は `ステータス` では表せない**（「このカットを使わない」）。`採否` を省略しない
- 案件で使わない列は**非表示にするだけ**（消さない）

### 素材使用DB
- ★`cut_key`(text) / ★`video_id`(text) / 使用素材rel(text) / 使用意図 / 台本との関係 / 注意・禁止
- relation: 動画/カット/素材(リンカー)

### 素材DB（=**編集制約台帳**。§7参照）
- 素材名(title) / 素材rel(text: カタログと共有のキー) / 種類 / 顔ルール / 音声BGM状態 / 使える秒数 / 禁止秒数 / verdict要約(text: verified_clips.jsonから転記)

### テロップチェックDB
- 行テキスト(title) / ★`video_id`(text) / `行No`(number) / cut id(text, cut_key文法) / 文字数(スペース除く)(number) / 表示秒数(number) / 字/秒(number) / 音量RMS実測(number) / フラグ(multi) / ステータス(select: 未確認/修正対象/修正中/修正済み/承認済み) / 元py / 採用v / 修正メモ / 最終更新(自動)
- relation: 動画(リンカー)

### プロジェクト台帳
- プロジェクト名(title) / クライアント / ステータス / 案件フォルダ / 納品フォルダ / 共通ルール
- ◆`納品ゲート結果`(text: `YYYY-MM-DD HH:MM PASS|FAIL <要約>` をnotion_gate.pyがスタンプ)

## 4. ステータス正規語彙（4系統。混用禁止、監査が検出）

| DB | 正規語彙 |
|---|---|
| 修正指示DB | 新規/確認中/設計済み/作業中/レンダー済み/検品中/修正完了/納品済み/却下/保留 |
| レンダーpy管理DB `採用状態` | 採用/却下/旧採用/未判定 |
| QAログDB `結果` | OK/NG/条件付きOK |
| 動画台帳 | 制作中/修正中/納品済み/アーカイブ |

**レガシー対応表**(監査が旧値を検出→変換提案): 確認済み→OK / 修正済み(指示DB文脈)→修正完了 / 要再確認→条件付きOK / 不採用→却下 / 検品待ち→未判定 / 破棄予定→却下 / 参考→却下(却下理由に"参考として保持"と書く)。

## 5. 履歴の構造

- **構造化履歴の正体 = レンダーpy管理DBの全行**(v・採用状態・却下理由・根拠・判定日)。却下一覧も採用遷移もクエリで復元できる。履歴専用DBは作らない。
- **人間可読の履歴 = 動画台帳ページ本文への日付付き追記**(VERSIONING§5書式)。リンカーがレンダー行から合成して追記する(冪等・追記のみ・消去禁止):
  `YYYY-MM-DD: v<NN>採用 ← v<MM>却下(<却下理由>)。根拠=<根拠>。py=<pyパス>`

## 6. 書式規約

- **秒数**: `<start>-<end>s`(例 `10.5-13.0s`) または単点 `12.5s`。語彙許可リスト: `冒頭`/`末尾`/`全体`。監査がregex検証。
- **パス**: 採用値は再生成可能なフルパスのみ。禁止パターン(監査FAIL): `pyなし`※ / `各build_*` / `詳細(py)?未確認` / `〜参照` 単体。
  ※原版コピー等でpyが本当に存在しない場合は `py不要(理由: <理由>)` の定型で書く(監査は定型のみ許可)。
- **cut id**: cut_key文法。`未確認`等のプレースホルダは監査FAIL。

## 7. 素材DB 2系統の役割(混同禁止)

| | 素材DB(案件テンプレ内) = **編集制約台帳** | vision解析DB = **素材カタログ** |
|---|---|---|
| 正本 | Notion(案件内) | SQLite(footage-asset-dbの成果物。Notionは鏡) |
| 行の条件 | 案件で「触った/使う判断をした」素材のみ | 全素材 |
| 内容 | 案件固有の制約・判断(顔NG/禁止秒数/verdict要約) | 客観メタ(尺/解像度/shot_type/vision説明) |
| 書き込み | ingest時にrelパスから自動起票+エージェント追記 | 再解析時のみ再生成。**案件判断の書き込み禁止** |

素材使用DBは編集制約台帳のみ参照(カタログ直参照は監査FAIL)。verified_clips.json(ローカル正本)のGO/NO-GO/BANNED要約はingestが編集制約台帳へ転記する。

## 8. 監査不変条件(notion_audit.pyが実装。FAILで納品不可)

1. **(video_id, バリアント)ごとに `採用状態=採用` の行はちょうど1つ**(0=未確定WARN、2以上=FAIL)
2. キーは文法regexに一致(不一致=FAIL)
3. キーがあるのにrelation欠落 → autolink対象(自動修復)。キーが解決不能(参照先の行が無い) → FAIL
4. 採用パスは§6のパス規約に一致(非パス参照=FAIL)
5. ステータスは§4正規語彙のみ(レガシー値=WARN+変換提案)
6. レンダー行があるのに対応する修正指示が終端ステータスでない期間が続く → WARN(ステータス放置検出)
7. ローカルの全(video_id, v)にNotionレンダー行が存在(check_adoption_sync[F]。却下版の未登録=FAIL)
8. cut_key孤児(カット台帳に無いcut_keyを他DBが参照)=FAIL、プレースホルダ(`未確認`)=FAIL
9. 動画台帳の◆派生列とレンダー採用行の値が一致(不一致=`整合`列に記録+FAIL)

## 9. ゲートとツール(実行タイミング)

| ツール | いつ |
|---|---|
| `notion_ingest_cutlist.py` | ビルド確定後(カットリスト→カット台帳/素材使用/テロップチェック一括起票) |
| `notion_log_render.py` | **レンダーするたび**(採用/却下問わずレンダー行+QAログ行を機械起票) |
| `notion_autolink.py --apply` | 作業セッション終了時 |
| `notion_gate.py` | **納品前・完了報告前に必須**(export→autolink→audit→check_adoption_sync[A]-[F]→プロジェクト台帳へPASS/FAILスタンプ)。完了報告にはPASSスタンプを引用する |

トークン解決: `NOTION_TOKEN`環境変数 → `--token-file` → `~/.claude.json`のnotionサーバー定義(既存保存場所の読み取りのみ。新たな永続化はしない)。トークンをログ・出力に出さない。

## 10. 変更管理

- この契約を変更したら: 正本を更新 → `sync_core.sh push` → スクリプトの実装追従 → テンプレページ本文の運用ルールブロック更新。
- 過去案件のDBには遡及強制しない(監査はWARN止まり)。新規行からFAIL適用。

### Notionに置く／置かない（境界・§1設計原則の具体化）
| 置く | 置かない（ローカルが正本・Notionはポインタ+サマリ） |
|---|---|
| 人が承認・裁定するもの（台本・停止点承認・conflict裁定・撮影申し送り） | 機械が再生成できる数値（asset_windows v2の全49列・全フレーム観察・pHash） |
| 履歴として残さないと再現できないもの（採用の変遷・却下理由・指摘の採否） | 中間生成物（frames/PNG/プロキシ） |
| 案件をまたいで参照するもの（学び・判断文法） | 数百行規模のカタログ全量（403行投入は2026-07-27にユーザー判断で見送り済み＝正しい判断） |

- 供給ギャップ（素材不足・次回撮影申し送り）は**修正指示DBに起票**する（DBを増やさない）
- 承認シート・参考動画1秒分析シートは**別テンプレのまま**、プロジェクト台帳からリンクで束ねる

### ★案件開始時の必須手順（重複作成の禁止・2026-07-30制定）
**新しくDBやページを作る前に、必ずNotion検索で既存インスタンスを確認する。**
2026-07-30に実際の事故: 既存の「案件O 動画制作管理」9DB体制（97行の修正記録DB含む）を
検索せずに同名DBと別ページを新規作成し二重管理を作った。復旧は「行を正本へ移動→誤作成側を
`【重複・使用しない／正本=...】` にリネーム」（削除ではなくリネーム＝履歴保全）。

### ★テンプレ更新時の既存インスタンスへの差分適用（必須）
テンプレ更新は既存の複製に自動反映されない。**複製し直すと案件の学びページ・既知の罠が失われるため、差分適用で行う**:
1. 追加DBは案件ページ配下に同じDDLで作る
2. 既存DBの列追加は `notion-update-data-source` の `ADD COLUMN`
3. 適用したことを案件ページに日付付きで追記する

## §10 ★時系列表示と複数本運用（2026-07-30制定・違反厳禁）

### §10-1 時系列は必須。設定して、さらに実際に引いて検証する
**時間軸を持つDBは、投入したら必ず「0秒から最後まで時系列に流れる」ビューを設定する。**
ユーザーから**3回**指摘された（承認シート/1秒分析シート/台本DB）。設定漏れは工程スキップと同じ扱い。

| DB | 主ソート | 副ソート | グループ |
|---|---|---|---|
| 台本DB | `採否` ASC（採用→DROP） | **`開始秒` ASC** | `video_id` |
| 工程・スケジュールDB | `順序` ASC | — | `video_id` |
| カット台帳 | `動画開始秒` ASC | — | `video_id` |
| 素材DB（窓） | `素材名` ASC | `t0秒` ASC | `回` |
| 1秒分析シート | `開始秒` ASC | — | 参考動画 |
| 承認シート | `tl秒` ASC | — | `video_id` |
| 修正指示DB | `受付日` ASC | — | `対象video_id` |
| QAログ/レンダーDB | `確認日`/`日付` ASC | — | `video_id` |

- **デフォルトビューも直す**（新規ビューを足すだけでは、ユーザーは先頭のデフォルトビューを開く）
- **台本DBのDROP行にも `開始秒` を入れる**（値=元発話のt0）。空だと採用行の後ろでバラバラに並ぶ
- ★**設定したら `query_database_view` で実際に引き、先頭が0秒・末尾が最終行であることを確認してから完了と言う**
  （申告だけで「時系列にした」と言わない）
- 実証（2026-07-30）: MCPの `create_view` / `update_view` の `SORT BY` と `GROUP BY` は**実ビューに反映される**。
  以前の「APIのsortsが効かないのでChrome UIで設定」という記録は**この日をもって訂正**（API可）

### §10-2 ★動画ごとに別ページを作り、そのページの中にDBを置く（2026-08-08 ユーザー指摘で訂正）

**★訂正履歴（2026-08-08）**: 本節は以前「1DBに全動画を入れる（動画ごとにDBを作らない）」と
書いていたが、**これは誤り**。ユーザー指摘の原文:
「動画ごとにDBを作らず1DBに全動画＋GROUP BY これが間違っている
　正確には動画ごとに別ページでDBを作る」
→ 正しい運用は **1動画 = 1ページ、そのページの中にその動画のDBを持つ**。

- **動画ごとに別ページを作る**。時間軸のあるDB（カット台帳・1秒分析シート・テロップチェック等）は
  **そのページの中に置く**。1つのDBに複数動画を混ぜない
- 理由: 選択肢（コンテカテゴリ・訴求機能など）が**動画/商材ごとに違う**ため、共有すると
  選択肢が汚れて使えなくなる。時系列ビューも動画をまたぐと0秒が複数現れて読めなくなる
- **案件 > 商材 > 動画** の階層でページを分ける（実運用例: Feriest 8月掲載分の商材ハブ）
- 各行の `video_id` は**引き続き必須**（ページをまたいで集計・突合するときの結合キーになる）
- キー文法（§1）を守る: `video_id` / `render_key`=`<video_id>_v<NN>` / `cut_key`=`<video_id>_c<NN>` /
  台本行=`<video_id>_S01` 相当（`行ID`＋`video_id`の組で一意）
- **版が変わったら行を消さず `台本v` を上げて新規行**（旧版は残す＝履歴保全）
- 案件全体を横断して見たいときは、**各動画DBを集計した要約表を親ページに置く**
  （DBを1つに統合するのではなく、親ページ側に一覧を持つ）

### §10-3 台本レビューの「修正」レーン（2026-07-30追加）
台本DBは**人がレビューして行単位で修正指示を出す**器でもある。そのための4列を持つ:

| 列 | 型 | 使い方 |
|---|---|---|
| `採否` | select | **採用 / 修正 / DROP / HOLD**。人が「修正」を選ぶと修正レーンに入る |
| `修正指示` | text | **人が書く**。何をどう直すか（原文で書いてよい） |
| `修正ステータス` | select | 未対応 / 対応中 / 対応済み / 却下（エージェントが更新） |
| `修正日` | date | 対応した日 |

運用: 人が `採否=修正` ＋ `修正指示` を書く → エージェントは**その行だけ**を直し、
ローカル正本(`script.json`)を更新して `修正ステータス=対応済み` ＋ `修正日` を打つ →
`備考` に何を変えたか（【R11修正】等のタグ付き）を追記して履歴を残す。
**動画単位の修正依頼は従来どおり修正指示DB**（粒度が違う。台本行の修正はこの4列で完結させ、DBを増やさない）。

### §10-4 状態遷移の可視化（2026-07-30追加。「後から追加した行がどこか分からない」問題の根治）
`採否` は**現在の状態**しか表さないため、後から採用に昇格した行が既存の採用行に紛れて判別不能になる。
遷移は**別列**で持つ（採否に「追加採用」を足すと時系列ソートが2グループに割れて§10-1に反するため）。

| 列 | 型 | 意味 |
|---|---|---|
| `変更区分` | select | **追加採用**(DROP/HOLD→採用) / **採用取消**(採用→DROP) / **保留化**(採用→HOLD) / **修正指定**(採用→修正) / **修正から復帰**(修正→採用) / **再DROP** |
| `変更履歴` | text | **追記のみ**。書式 `YYYY-MM-DD v<台本v>: 旧→新（理由）` |
| `初回採否` | select | 最初に確定した採否。遷移時に旧値を入れる（空欄=一度も変わっていない） |

- 遷移が起きたら**3列すべてを同時に更新**する（片方だけ書かない）
- **空欄=変更なし**なので、`変更区分 IS NOT EMPTY` のビュー1枚で「追加・変更された行」が全部引ける
- 必須ビュー2枚: **★本編の時系列**（`採否 != DROP AND != HOLD` / `開始秒` ASC＝0秒から流れる）と
  **★追加・変更のみ**（`変更区分 IS NOT EMPTY`）
- ★**select列の ALTER COLUMN SET の直後は必ず全行の値をクエリで検算する**。
  2026-07-30に `採否` のALTER前後で**1行だけ値が DROP→採用 に化けた**（実クエリで検出・復旧）。
  スキーマ変更は既存データを壊し得るので、変更→検算→修復までを1セットで行う

### §10-5 ★ユーザーの操作を「データ化け」と誤診して上書きしない（2026-07-30・実際に起こした事故）
Notionの値が自分の記録と食い違ったとき、**最初に検討すべきは「ユーザーが操作した」可能性**である。

**起こした事故**: ユーザーが台本DBの1行を `DROP→採用`（追加採用）に変更したのを、Claudeが
「select列のALTER COLUMNで値が化けた」と誤診し、**ユーザーの判断を勝手にDROPへ戻した**。
さらに変更履歴に「スキーマ変更で化けた」という**誤った説明を書き込んだ**。

**恒久ルール**:
1. 自分の記録と違う値を見つけたら、**まず変更履歴・変更区分・最終更新を確認**し、
   ユーザー操作の痕跡を探す。痕跡がなくても**上書きする前にユーザーに確認する**（値の復元は破壊的操作）
2. 直近に自分がスキーマ変更をしていても、それを第一の容疑者にしない
   （2026-07-30の件は、ALTER COLUMNとユーザー操作の時刻が偶然近かっただけ）
3. 誤って上書きした場合は、**変更履歴に誤診と撤回を明記**して復旧する（消さずに残す）
