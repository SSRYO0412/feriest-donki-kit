# REVISION-LEDGER — 修正台帳（`revision_ledger`）の設計・作成・運用

> **修正案件で最も重要な成果物**。ユーザー／クライアントが修正指示を出す唯一の窓口であり、
> 「どのカットを・なぜ・どう直したか」の全履歴がここに残る。**動画を触る前に、これを作る。**
>
> 正本: `_video-core/revision/references/REVISION-LEDGER.md`（= `video-ops-framework/core/`）。
> 改善したら `sync_core.sh pull` → `push` で配布先へ反映する。
> 上位規約は `ledger-db-contract.md`（キー文法・語彙・監査）と `VERSIONING.md`（版管理・履歴書式）。
>
> ★**置き場所は VOPS Ledger の `revision_ledger`（`scope: per-video`）**。Notion ではない（契約§0）。
> 既存の Notion 案件は据え置き。新規案件は台帳で作る。

## 0. なぜ最重要か

修正案件の事故は、ほぼ全部ここに集約される。

- 指示がチャットに散り、**何が未対応か誰も言えなくなる**
- 「前に直したはず」の修正が次の版で**戻る**（回帰）
- 採用版が動いたのに台帳が古く、**古いMP4を納品する**
- 指示の原文が残らず、**解釈違いのまま作り直しになる**

修正台帳は「指示の受付」「作業の進捗」「採用版の真実」「やり直さないための履歴」を
1箇所に束ねる。**ここが正で、チャットは正ではない。**

## 1. 「修正台帳」は2つある（混同禁止）

| | `revision_ledger`（本書） | `ledger.md`（VERSIONING §3） |
|---|---|---|
| 実体 | **VOPS Ledger の `revision_ledger`**（動画ごとに `video_id` で分かれる） | 案件ルート直下のMarkdown 1ファイル |
| 読む人 | **ユーザー／クライアント**と作業者 | 作業者だけ |
| 役割 | **指示の受付**と全履歴の正本 | 作業中のミラー／下書き |
| 正・副 | **正** | 副（台帳が正） |

**ユーザーが書き込むのは台帳側だけ。** `ledger.md` に指示を書かせてはいけない。

## 2. 全体構造（★Notion のページ階層は不要になった）

Notion 時代は「親ページ＋動画ごとの子ページ＋ページ内DB」で分離していた。
台帳では **1つの `revision_ledger` を `video_id` で分ける**（契約§10-2）。要件は同じで、実現手段だけが変わった。

```
project_id = <案件>                      ← 案件の単位
  revision_ledger                        ← 修正台帳（scope: per-video）
    video_id=0385_01 の行（13カット）     ← 動画1本ぶん。UIは動画を選んでから中に入る
    video_id=0386_01 の行（13カット）
    …
  project_ledger.修正巡目まとめ           ← 巡目ごとのまとめ（旧・親ページ本文。§6）
  video_ledger.過去修正メモ               ← 動画1本の採用履歴（旧・動画ページ本文。VERSIONING §5）
```

実例（案件V official 260730 ab版10本 = 130行が `video_id` で10本に分かれる）。

- ★**動画ごとに別DBを作らない。** db_key は13個で固定（契約§0.2）
- ★**`video_id` は全行必須。** これが無いと動画で分けられず、0秒が複数現れて読めなくなる
- 版（`(vNN)`）は行の属性ではなく `render_db` が持つ。**台帳の行名に版を埋め込まない**

## 3. 設計方法

### 3.1 動画の分け方（判断は不要になった）

Notion 時代は「動画ごとに専用DB」か「共有DB＋リンクドビュー」かを案件ごとに選んでいた。
**台帳では選択肢が無い**（`scope: per-video` の1択）。理由は元の判断規則と同じものを両方満たすため。

| 元の懸念 | 台帳での解決 |
|---|---|
| `コンテカテゴリ` 等の選択肢が動画/商材ごとに違い、共有すると汚れる | `schema_edit` に `project_id` を付ければ**案件ごとの差分**になる。会社共通は汚れない。選択肢は `open: true` なので現場で足せる |
| 時系列ビューが動画をまたぐと0秒が複数現れる | ビューの `group_by: video_id` ＋ **UIは動画を選んでから中に入る**／MCPは `ledger_query` の `video_id` で絞る |

**「1動画ずつ・0秒から時系列・`修正指示` と `採否` を左に」は必ず守る**（ここは不変）。

### 3.2 列の構成（31列。案件V＋案件F の実運用を統合したもの）

`revision_ledger` の既定スキーマ。列名は台帳の `schema_list` が正。

**①キーと時間軸**（起票時に機械が入れる）

| 列 | 型 | 用途 |
|---|---|---|
| `カット名` | title | `cNN 「テロップ文言」` の形 |
| `cut id` / `cut_key` / `video_id` | text | `cut_key`=`<video_id>_c<NN>`。他DBとの結合キー。★`record_id` にも `cut_key` を使う |
| `動画内開始秒` / `動画内終了秒` / `尺` | number | ★**並び順の根拠**。0秒から昇順 |

**②内容（どの絵かを言葉で特定するため）**

| 列 | 用途 |
|---|---|
| `テロップ文言` | ★秒が分からなくても言葉で行を特定できる。**これが無いとユーザーは行を探せない** |
| `台本/VO文言` | 訴求と絵の一致を判定する |
| `コンテカテゴリ` | 絵コンテ側の区分（コンテがある案件） |
| `使用意図` | なぜこの絵か |

**③受付（★人が書くのはこの2列だけ）**

| 列 | 型 | 用途 |
|---|---|---|
| **`修正指示`** | text | 何をどう直すか |
| **`採否`** | select: 採用/**修正**/**DROP**/HOLD | 修正・DROP が作業対象。**DROP は「このカットを使わない」で、`ステータス` では表せない** |

**④進捗・履歴（作業側）**

| 列 | 型 | 用途 |
|---|---|---|
| `ステータス` | select: 未確認/確認済み/要修正/対応中/修正済み/却下 | 進捗 |
| `初回採否` | select: 採用/修正/DROP/HOLD | 初回の判断を固定（比較用） |
| `変更区分` | select: 新規/差し替え/追加採用/採用取消/置かないへ変更/修正指定/修正から復帰/再DROP | **遷移が起きた時のみ** |
| `変更履歴` | text | **追記のみ** `YYYY-MM-DD 旧→新(理由)`。追記は read-modify-write（`ledger_get` → 末尾に足して `ledger_upsert`） |
| `DROP理由` / `却下理由` | text | 落とした理由（消さない） |
| `修正日` | date | |
| `選定版` | text | どの選定ラウンドの結果か |

**⑤素材と画（差し替えを再現可能にする）**

| 列 | 用途 |
|---|---|
| `使用素材名` ＋ `素材内開始秒 tin` / `素材内終了秒 tout` | 差し替え先を再現可能に |
| `スケール` | 寄り引き（等倍=1.0） |
| `モーション` | パン/ズーム/静止 |
| `人物判定` | demo(実演)/pass(横切り)/edge(映り込み)/none |
| `クロップ指定` / `顔あり/顔なし指定` | 画角・素材ルール |
| `BGM/SEメモ` / `注意事項` | 音の指示・その他 |

★**`修正指示`・`採否`・`テロップ文言`・`動画内開始秒` の4つは必須。**
この4つが揃っていないと、ユーザーは動画を見ながら行を特定して書き込めない。
案件で使わない列（`コンテカテゴリ`・`人物判定` 等）は**ビューから外すだけ**でよい（消さない）。

### 3.3 ビュー設定（`ledger-db-contract` §10 準拠）

既定ビュー `0秒から時系列（記入用）` が最初から入っている。案件で列を足したら**ビューにも足す**。

```
schema_edit(project_id=<案件>, db_key="revision_ledger", ops=[{
  "op":"set_view", "name":"0秒から時系列（記入用）", "type":"table",
  "display_properties":["カット名","動画内開始秒","テロップ文言","修正指示","採否",
                        "ステータス","使用素材名","変更履歴"],
  "sorts":[{"property":"動画内開始秒","direction":"ascending"}],
  "group_by":"video_id", "first":true }])
```

- **ソート: `動画内開始秒` ASC**（=0秒から時系列）。カット順に並んでいないと、ユーザーは
  動画を見ながら行を探せない
- **グループ: `video_id`**（動画をまたいで秒数が混ざらない）
- ★**`first: true` で既定ビューにする。** 新規ビューを足すだけでは、ユーザーが最初に開くビューが
  時系列になっていない（ユーザーから3回指摘された事故）
- ★**`ledger_query` で実際に引き、先頭が0秒・末尾が最終カットであることを確認してから
  「作った」と言う。** 設定した申告だけで完了報告しない
- 列順は左から `カット名 / 動画内開始秒 / テロップ文言 / 修正指示 / 採否 / ステータス` を推奨。
  **`修正指示` と `採否` は横スクロールなしで見える位置に置く**（見えない欄には書かれない）
- ★**ビューに載せた列をスキーマから消すと、UI は黙って全列表示に落ちる**（列を消すときはビューも直す）

### 3.4 案内文（ユーザーへ渡すときに必ず添える1行）

Notion 時代は子ページ本文の1行目に書いていた。台帳にページ本文は無いので、
**UI の URL を渡すメッセージ本文に書く**（同じ内容を `project_ledger.備考` にも残す）。

```
<納品ファイル名> の全<N>カット。0秒から時系列。「修正指示」列にご記入ください。
```

実例: `mov_official_0385_01_ab_lp001_v1.mp4 の全13カット。0秒から時系列。「修正指示」列にご記入ください。`

- **納品ファイル名を書く**（どの版に対する指示かが確定する）
- **カット数を書く**（行の抜けに気づける）

## 4. 作成手順（新規案件）

1. **`schema_list` で既存を確認する**（契約§0.1）。db_key は13個で固定なので、
   Notion 時代の「同名DBを二重に作る」事故（2026-07-30）は構造的に起こらない。
   確認するのは「この `project_id` にもう行が入っていないか」
2. 案件を台帳に用意する（`vops new … --ledger-backend vops`、または
   `notion_bootstrap.py vops:<project_id>`。冪等・既存はskip）
3. 案件固有の列・選択肢を `schema_edit`（`project_id` 付き＝その案件だけ）で足す
4. **行を機械起票する**。手転記しない — `scripts/notion_ingest_cutlist.py` が
   カットリストJSON → `cut_ledger`／`asset_use_db`／`telop_check_db` へ冪等に起票する。
   `revision_ledger` へは同じカットリストから `cut_key`・`動画内開始秒`・`テロップ文言`・`使用意図`・
   `使用素材名`・`tin`/`tout`・`スケール`・`初回採否` を写す
   （★`修正指示` と `採否` は**空のまま**ユーザーへ渡す）
5. §3.3 のビューを設定する（`first: true`）
6. `ledger_query`（`video_id` 指定）で**引いて検証**（先頭0秒・行数＝カット数）
7. `video_ledger` にこの時点の採用版（`採用MP4パス`/`最終v`）が入っていることを確認する
8. ユーザーへ **UI の URL** を渡す。**「どこに何を書くか」を1文で添える**（§3.4）

## 5. 運用フロー

```
ユーザーが UI の「修正指示」列に記入し、「採否」を 修正 / DROP にする
        ↓
作業側が着手前に全行を読む（ledger_query）＋ video_ledger で現在の採用版を確認
        ↓ ★過去の「保持すべき修正」を先に列挙（回帰させないため）
差し替え／修正を実装 → 新しいv番号で出力（上書き禁止）
        ↓
行を埋める（ledger_upsert・触った列だけ）: 変更区分 / 使用素材名 / tin-tout / DROP理由 / 変更履歴 / 修正日
ステータス → 修正済み
        ↓
render_db・qa_log_db へ記録 → video_ledger の採用版を更新
        ↓
project_ledger.修正巡目まとめ へ巡目まとめを追記（§6）
```

### 5.1 着手前（必ず全部やる）

- [ ] `ledger_query`（`db_key=revision_ledger`・`video_id` 指定）で**全行**を読む
      （`修正指示` が空でない行・`採否`＝修正/DROP の行を漏らさない）
- [ ] `video_ledger` で現在の採用MP4・採用py を確認
- [ ] **過去の修正指示を全部読み、「保持すべき修正」を列挙**する。
      新しい修正で古い修正を戻さない（回帰は最も多い事故）。`過去修正メモ` と `ledger_history` の両方を見る
- [ ] 対象カットを `cut_key` で特定（`未確認` 等のプレースホルダは監査FAIL）
- [ ] 指示が曖昧なら**着手前に1問だけ聞く**。推測で作って作り直すより安い

### 5.2 実装中

- **指示された範囲を超えて直さない。** 「良さそうだから」で素材変更・クロップ変更・
  BGM変更をしない。必要なら先に理由を出して確認する
- **完成MP4を直接編集しない。** py から再生成する
- **上書きしない。** 却下版も残す（`VERSIONING` §2 の命名で py と MP4 の v を一致させる）

### 5.3 反映（1カットずつ埋める）

指示1件に対して、そのカット行に必ず残す（`ledger_upsert` は触った列だけでよい）。

| 列 | 書き方 |
|---|---|
| `変更区分` | 追加採用／採用取消／保留化／修正指定／修正から復帰／再DROP。**遷移が起きた時のみ** |
| `使用素材名` ＋ `tin`/`tout` | 差し替え先を再現可能な形で |
| `DROP理由` | なぜ落としたか（次に同じ絵を選ばないため。消さない） |
| `変更履歴` | **追記のみ** `YYYY-MM-DD 旧→新(理由)`。現在値を読んでから足す |
| `ステータス` | 修正済み |
| `修正日` | 実施日 |

★**「直した」と報告する前に、出力物で反映を確認する。** レンダーし直して、
そのカットの実フレームを見る。台帳を埋めただけで完了にしない。

### 5.4 やってはいけないこと

- **行を消さない**（対応済みは `ステータス` 変更で履歴として残す。どうしても隠すなら `status: archived`）
- **まとめて後で書かない**（採用が動いた瞬間に書く。`VERSIONING` §4）
- **ゲート未通過で完了報告しない**（`notion_gate.py vops:<project_id>` の PASS を引用する）

## 6. 巡目まとめの追記先 = `project_ledger.修正巡目まとめ`（上書き消去 厳禁）

Notion 時代の親ページ本文の置き換え。**進捗と履歴の正本**で、巡目ごとに日付付きで追記する。
台帳の text 列なので、**`ledger_get` で現在値を読み、末尾に足して `ledger_upsert`**（read-modify-write）。

必ず入れる要素:

1. **先方／ユーザー指摘の原文引用** — 要約しない。解釈違いの再発を防ぐ唯一の手段
2. **何をどう直したか**（対象 `cut_key` と差し替え先素材・秒数）
3. **判断根拠** — 全フレーム目視／機械検査PASS／現物確認／ユーザー承認（`VERSIONING` §5 の語彙）
4. **最終版の採用v一覧**（全動画ぶん・毎回全部書き直す）
5. **未対応・申し送り**（★印で明示）

実例:

```
**2026-08-04 深夜 5巡目修正**: 先方指摘「他と同じカット使わないでって言ったよね。
ヨリで、ソール部分が映ってて、カメラの動きは少ないもの」。4巡目で導入した
ALTIVO_B_08/B_10の使い回し(各3〜4動画で重複)を解消し、0385_01 c10/0386_01 c10/… を、
他動画で未使用の新規素材(ALTIVO_B_11・IMG_3882・…)へ差し替え。全てslow=1.0・crop無し。
全10本 qc_mech.py 再PASS。
最終版: 0385_01=v53 / 0386_01=v57 / … / 0394_01=v57。
★注記: 今回未対応だが同様の重複が残る箇所(0390_01_c02=ALTIVO_B_11、…)を検算で確認。
指示があれば対応。
```

- **採用v一覧は巡目ごとに全部書き直す**（差分だけ書くと、どれが最新か分からなくなる）
- **未対応を隠さない。** 「検算で確認したが今回は触っていない」を明記する。
  これを書かないと、次の巡で「なぜ直っていない」になる
- 動画1本ぶんの採用履歴は `video_ledger.過去修正メモ`（VERSIONING §5 書式・リンカーが生成）。
  **巡目まとめ（案件横断の物語）とは別物なので、片方で済ませない**

## 8. `revision_request_db` との関係

`revision_ledger`（修正台帳）と `revision_request_db`（修正指示DB）は**役割が違う。両方使う。**

| | `revision_ledger` | `revision_request_db` |
|---|---|---|
| 粒度 | **1カット = 1行** | 1指示 = 1行 |
| 並び | 動画の時間軸（0秒から） | 指示の受付順 |
| 得意 | 「この絵をこう直して」— 対象が絵で特定できる指示 | 「全動画のテロップを大きく」— 横断・方針レベルの指示 |
| 接続 | `cut_key` / `video_id` で結合（relationはリンカーが張る） | 同左 |

**カット単位で特定できる指示は修正台帳へ、横断・方針レベルは修正指示DBへ。**
どちらに書かれたものも指示として同格に扱う。修正指示DB側の書式（`対象秒数` は
`10.5-13.0s` 形式・`対象cut id` は cut_key 文法）は `ledger-db-contract` §6 に従う。
