# REVISION-LEDGER — 修正台帳（Notion）の設計・作成・運用

> **修正案件で最も重要な成果物**。ユーザー／クライアントが修正指示を出す唯一の窓口であり、
> 「どのカットを・なぜ・どう直したか」の全履歴がここに残る。**動画を触る前に、これを作る。**
>
> 正本: `_video-core/revision/references/REVISION-LEDGER.md`（= `video-ops-framework/core/`）。
> 改善したら `sync_core.sh pull` → `push` で配布先へ反映する。
> 上位規約は `notion-db-contract.md`（キー文法・語彙・監査）と `VERSIONING.md`（版管理・履歴書式）。

## 0. なぜ最重要か

修正案件の事故は、ほぼ全部ここに集約される。

- 指示がチャットに散り、**何が未対応か誰も言えなくなる**
- 「前に直したはず」の修正が次の版で**戻る**（回帰）
- 採用版が動いたのに台帳が古く、**古いMP4を納品する**
- 指示の原文が残らず、**解釈違いのまま作り直しになる**

修正台帳は「指示の受付」「作業の進捗」「採用版の真実」「やり直さないための履歴」を
1箇所に束ねる。**ここが正で、チャットは正ではない。**

## 1. 「修正台帳」は2つある（混同禁止）

| | Notion 修正台帳（本書） | `ledger.md`（VERSIONING §3） |
|---|---|---|
| 実体 | Notionのページ群＋修正台帳DB | 案件ルート直下のMarkdown 1ファイル |
| 読む人 | **ユーザー／クライアント**と作業者 | 作業者だけ |
| 役割 | **指示の受付**と全履歴の正本 | 作業中のミラー／下書き |
| 正・副 | **正** | 副（Notionが正） |

**ユーザーが書き込むのは Notion 側だけ。** `ledger.md` に指示を書かせてはいけない。

## 2. 全体構造

```
<案件> 修正管理（既存の管理ページ配下）
  └ 📋 <日付> <系統> 修正台帳(<動画ID範囲> <版>)      ← 束ねる親ページ
      │   本文 = 採用版一覧 ＋ 巡目ごとの修正まとめ（日付付き追記・§6）
      ├ <video_id> (v<NN>) 修正台帳                   ← 動画1本 = 1ページ
      │   本文 = 案内文1行 ＋ 修正台帳のビュー（0秒から時系列）
      ├ <video_id> (v<NN>) 修正台帳
      └ …（動画の本数ぶん）
```

実例（案件V official 260730 ab版10本）:

```
📋 260730 official 修正台帳(0385-0394 ab版)
  ├ 0385_01 (v2) 修正台帳     ← 全13カット
  ├ 0386_01 (v9) 修正台帳
  └ … 全10本 = 130カット
```

- ページタイトルの `(vNN)` は**台帳を作った時点の版**。採用版が動いても改名しない
  （改名するとリンクが追えなくなる。最新の採用版は親ページ本文で管理する）
- **動画ごとにページを分ける**。1ページに複数動画を詰めない（§3.1）

## 3. 設計方法

### 3.1 DBを分けるか、共有DBのビューにするか

`notion-db-contract` §10-2 の原則は **「動画ごとに別ページを作り、そのページの中にDBを置く。
1つのDBに複数動画を混ぜない」**。理由は2つ。

1. **選択肢が汚れる** — `コンテカテゴリ`・訴求機能などの select 候補は動画/商材ごとに違う。
   共有すると候補が増え続けて使えなくなる
2. **時系列ビューが読めなくなる** — 動画をまたぐと0秒が複数現れる

判断規則:

| 条件 | 構成 | 実例 |
|---|---|---|
| 商材・構成・選択肢が**動画ごとに違う** | **動画ごとに専用DB**を各ページ内に作る（**既定**） | Feriest（`short_ver_v2 カット台帳` を動画ごとに新規作成） |
| **同一商材の同一構成バリアント量産**（選択肢が完全に共通） | 1つのDB＋**動画ごとのリンクドビュー**（`video_id` でフィルタ） | 案件V ab版10本（同じ13カット構成） |

**どちらを採っても「1ページ＝1動画・0秒から時系列・`修正指示` と `採否` を左に」は必ず守る。**
テンプレの子ページには両方が入っているので、使わない方のブロックを複製後に削除する。

### 3.2 列の構成（統合版）

テンプレの子ページ内DB `<video_id> カット台帳（全<N>カット・0秒から時系列）` が既定のスキーマ。
案件V（受付・履歴が厚い）と Feriest（絵の設計値が厚い）の両方の実運用を統合した31列。

**①キーと時間軸**（起票時に機械が入れる）

| 列 | 型 | 用途 |
|---|---|---|
| `カット名` | title | `cNN 「テロップ文言」` の形 |
| `cut id` / `cut_key` / `video_id` | text | `cut_key`=`<video_id>_c<NN>`。他DBとの結合キー |
| `動画内開始秒` / `動画内終了秒` / `尺` | number | ★**並び順の根拠**。0秒から昇順 |

**②内容（どの絵かを言葉で特定するため）**

| 列 | 用途 |
|---|---|
| `テロップ文言` | ★秒が分からなくても言葉で行を特定できる。**これが無いとユーザーは行を探せない** |
| `台本/VO文言` | 訴求と絵の一致を判定する |
| `コンテカテゴリ` | 絵コンテ側の区分（コンテがある案件） |
| `使用意図` | なぜこの絵か |

**③受付（★人が書くのはこの2列だけ）**

| 列 | 型 | 用途 |
|---|---|---|
| **`修正指示`** | text | 何をどう直すか |
| **`採否`** | select: 採用/**修正**/**DROP**/HOLD | 修正・DROP が作業対象。**DROP は「このカットを使わない」で、`ステータス` では表せない** |

**④進捗・履歴（作業側）**

| 列 | 型 | 用途 |
|---|---|---|
| `ステータス` | select: 未確認/確認済み/要修正/対応中/修正済み/却下 | 進捗 |
| `初回採否` | select: 採用/修正/DROP/HOLD | 初回の判断を固定（比較用） |
| `変更区分` | select: 新規/差し替え/追加採用/採用取消/置かないへ変更/修正指定/修正から復帰/再DROP | **遷移が起きた時のみ** |
| `変更履歴` | text | **追記のみ** `YYYY-MM-DD 旧→新(理由)` |
| `DROP理由` / `却下理由` | text | 落とした理由（消さない） |
| `修正日` | date | |
| `選定版` | text | どの選定ラウンドの結果か |

**⑤素材と画（差し替えを再現可能にする）**

| 列 | 用途 |
|---|---|
| `使用素材名` ＋ `素材内開始秒 tin` / `素材内終了秒 tout` | 差し替え先を再現可能に |
| `スケール` | 寄り引き（等倍=1.0） |
| `モーション` | パン/ズーム/静止 |
| `人物判定` | demo(実演)/pass(横切り)/edge(映り込み)/none |
| `クロップ指定` / `顔あり/顔なし指定` | 画角・素材ルール |
| `BGM/SEメモ` / `注意事項` | 音の指示・その他 |

★**`修正指示`・`採否`・`テロップ文言`・`動画内開始秒` の4つは必須。**
この4つが揃っていないと、ユーザーは動画を見ながら行を特定して書き込めない。
案件で使わない列（`コンテカテゴリ`・`人物判定` 等）は非表示にするだけでよい（消さない）。

**共有DB方式を採る場合**は `映像管理_修正台帳`（`collection://c4e0ae61-7f24-4abf-95fa-d81ba09040f0`）
を使う。列名が一部違う（`発話`＝テロップ文言、`src範囲`＝tin/tout、`修正ステータス`＝ステータス）。

### 3.3 ビュー設定（`notion-db-contract` §10 準拠）

- **ソート: `動画内開始秒` ASC**（=0秒から時系列）。カット順に並んでいないと、ユーザーは
  動画を見ながら行を探せない
- **フィルタ: `video_id` = その動画**（リンクドビュー構成の場合）
- ★**デフォルトビューも直す。** 新規ビューを足すだけでは、ユーザーが最初に開くビューが
  時系列になっていない（ユーザーから3回指摘された事故）
- ★**`query_database_view` で実際に引き、先頭が0秒・末尾が最終カットであることを確認してから
  「作った」と言う。** 設定した申告だけで完了報告しない
- 列順は左から `カット名 / 動画内開始秒 / テロップ文言 / 修正指示 / 採否 / ステータス` を推奨。
  **`修正指示` と `採否` は横スクロールなしで見える位置に置く**（見えない欄には書かれない）

### 3.4 案内文の定型（子ページ本文の1行目）

```
<納品ファイル名> の全<N>カット。0秒から時系列。「修正指示」列にご記入ください。
```

実例: `mov_official_0385_01_ab_lp001_v1.mp4 の全13カット。0秒から時系列。「修正指示」列にご記入ください。`

- **納品ファイル名を書く**（どの版に対する指示かが確定する）
- **カット数を書く**（行の抜けに気づける）

## 4. 作成手順（新規案件）

1. **既存インスタンスを検索する**（`notion-db-contract` §9）。同名の管理ページ・DBを
   作る前に必ず Notion 検索。2026-07-30 に二重管理を作った事故がある
2. 汎用テンプレの **「修正台帳（テンプレ）」を複製**して案件の管理ページ配下に置き、
   `📋 <日付> <系統> 修正台帳(<範囲> <版>)` にリネーム（§7）
3. 修正台帳DBを用意する（§3.1 の判断規則・§3.2 の列。案件固有の列は `ADD COLUMN`）
4. **行を機械起票する**。手転記しない — `scripts/notion_ingest_cutlist.py` が
   カットリストJSON → カット台帳／素材使用DB／テロップチェックDB へ冪等に起票する。
   修正台帳へは同じカットリストから `cut_key`・`動画内開始秒`・`テロップ文言`・`使用意図`・
   `使用素材名`・`tin`/`tout`・`スケール`・`初回採否` を写す
   （★`修正指示` と `採否` は**空のまま**ユーザーへ渡す）
5. 動画ごとに**子ページ**を作り、ビューを埋め、§3.3 のソート／フィルタを設定
6. §3.4 の案内文を入れる
7. `query_database_view` で**引いて検証**（先頭0秒・行数＝カット数）
8. 親ページ本文に、この時点の**採用版一覧**を書く
9. ユーザーへ URL を渡す。**「どこに何を書くか」を1文で添える**

## 5. 運用フロー

```
ユーザーが「修正指示」列に記入し、「採否」を 修正 / DROP にする
        ↓
作業側が着手前に全行を読む ＋ 動画台帳で現在の採用版を確認
        ↓ ★過去の「保持すべき修正」を先に列挙（回帰させないため）
差し替え／修正を実装 → 新しいv番号で出力（上書き禁止）
        ↓
行を埋める: 変更区分 / 使用素材名 / tin-tout / DROP理由 / 変更履歴 / 修正日
ステータス → 修正済み
        ↓
レンダーpy管理DB・QAログDBへ記録 → 動画台帳の採用版を更新
        ↓
親ページ本文へ巡目まとめを追記（§6）
```

### 5.1 着手前（必ず全部やる）

- [ ] 子ページの**全行**を読む（`修正指示` が空でない行・`採否`＝修正/DROP の行を漏らさない）
- [ ] `動画台帳` で現在の採用MP4・採用py を確認
- [ ] **過去の修正指示を全部読み、「保持すべき修正」を列挙**する。
      新しい修正で古い修正を戻さない（回帰は最も多い事故）
- [ ] 対象カットを `cut_key` で特定（`未確認` 等のプレースホルダは監査FAIL）
- [ ] 指示が曖昧なら**着手前に1問だけ聞く**。推測で作って作り直すより安い

### 5.2 実装中

- **指示された範囲を超えて直さない。** 「良さそうだから」で素材変更・クロップ変更・
  BGM変更をしない。必要なら先に理由を出して確認する
- **完成MP4を直接編集しない。** py から再生成する
- **上書きしない。** 却下版も残す（`VERSIONING` §2 の命名で py と MP4 の v を一致させる）

### 5.3 反映（1カットずつ埋める）

指示1件に対して、そのカット行に必ず残す。

| 列 | 書き方 |
|---|---|
| `変更区分` | 追加採用／採用取消／保留化／修正指定／修正から復帰／再DROP。**遷移が起きた時のみ** |
| `使用素材名` ＋ `tin`/`tout` | 差し替え先を再現可能な形で |
| `DROP理由` | なぜ落としたか（次に同じ絵を選ばないため。消さない） |
| `変更履歴` | **追記のみ** `YYYY-MM-DD 旧→新(理由)` |
| `ステータス` | 修正済み |
| `修正日` | 実施日 |

★**「直した」と報告する前に、出力物で反映を確認する。** レンダーし直して、
そのカットの実フレームを見る。台帳を埋めただけで完了にしない。

### 5.4 やってはいけないこと

- **行を消さない**（対応済みは `ステータス` 変更で履歴として残す）
- **まとめて後で書かない**（採用が動いた瞬間に書く。`VERSIONING` §4）
- **ゲート未通過で完了報告しない**（`notion_gate.py` の PASS を引用する）

## 6. 親ページ本文への履歴追記（上書き消去 厳禁）

親ページ本文が**進捗と履歴の正本**になる。巡目ごとに日付付きで追記する。

必ず入れる要素:

1. **先方／ユーザー指摘の原文引用** — 要約しない。解釈違いの再発を防ぐ唯一の手段
2. **何をどう直したか**（対象 `cut_key` と差し替え先素材・秒数）
3. **判断根拠** — 全フレーム目視／機械検査PASS／現物確認／ユーザー承認（`VERSIONING` §5 の語彙）
4. **最終版の採用v一覧**（全動画ぶん・毎回全部書き直す）
5. **未対応・申し送り**（★印で明示）

実例:

```
**2026-08-04 深夜 5巡目修正**: 先方指摘「他と同じカット使わないでって言ったよね。
ヨリで、ソール部分が映ってて、カメラの動きは少ないもの」。4巡目で導入した
ALTIVO_B_08/B_10の使い回し(各3〜4動画で重複)を解消し、0385_01 c10/0386_01 c10/… を、
他動画で未使用の新規素材(ALTIVO_B_11・IMG_3882・…)へ差し替え。全てslow=1.0・crop無し。
全10本 qc_mech.py 再PASS。
最終版: 0385_01=v53 / 0386_01=v57 / … / 0394_01=v57。
★注記: 今回未対応だが同様の重複が残る箇所(0390_01_c02=ALTIVO_B_11、…)を検算で確認。
指示があれば対応。
```

- **採用v一覧は巡目ごとに全部書き直す**（差分だけ書くと、どれが最新か分からなくなる）
- **未対応を隠さない。** 「検算で確認したが今回は触っていない」を明記する。
  これを書かないと、次の巡で「なぜ直っていない」になる

## 8. 修正指示DB との関係

修正台帳（カット台帳）と `修正指示DB` は**役割が違う。両方使う。**

| | 修正台帳（カット台帳） | 修正指示DB |
|---|---|---|
| 粒度 | **1カット = 1行** | 1指示 = 1行 |
| 並び | 動画の時間軸（0秒から） | 指示の受付順 |
| 得意 | 「この絵をこう直して」— 対象が絵で特定できる指示 | 「全動画のテロップを大きく」— 横断・方針レベルの指示 |
| 接続 | `関連修正指示` relation | 逆参照で見える |

**カット単位で特定できる指示は修正台帳へ、横断・方針レベルは修正指示DBへ。**
どちらに書かれたものも指示として同格に扱う。修正指示DB側の書式（`対象秒数` は
`10.5-13.0s` 形式・`対象cut id` は cut_key 文法）は `notion-db-contract` §6 に従う。
