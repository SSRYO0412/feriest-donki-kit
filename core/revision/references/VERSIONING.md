# 映像案件 バージョン管理・履歴保全 規約（VERSIONING）

> 正本: `~/.claude/skills/_video-core/revision/references/VERSIONING.md`（sync_core.sh で配布）。
> 全映像案件（制作・修正・量産）に適用する案件非依存の規約。案件固有の数値・パスは含まない。
> 由来: VERARUS 2026-07-10 事故（最終検品フォルダのMP4が古い版／採用pyがmtime最新版と別で、どれが採用版か迷子になった）。ローカルのファイル日時・会話の記憶を根拠にすると必ず事故る。

## 0. 正本（source of truth）の定義

- **編集の正本 = `py + 元素材 + VO/BGM/生成音声 + CTA素材 + 中間素材`**。完成MP4は確認用・納品用であり正本ではない。
- **採用状態の正本 = 管理DB（Notion動画台帳）**。ローカルのファイル日時（mtime）・会話の記憶・「たぶんこれが最新」は根拠にならない。
- 完成MP4を直接編集・パッチしない。必ずpy/sourceから再レンダーする。

## 1. v番号規約

1. **出力するたびにvを進める**。同じファイル名での上書きは絶対禁止。
2. **失敗版・却下版も欠番にしない・削除しない**。「どのvが何故ダメだったか」が履歴の一部。
3. vは動画ID単位で単調増加（バリアントA/Bを持つ場合はバリアントごとに独立採番し、必ず双方を台帳に併記する）。
4. 「最新v」と「採用v」は別概念。**採用vは管理DBに書かれたものだけが真**（最新=採用とは限らない）。

## 2. 命名規約

| 種別 | 形式 | 例 |
|---|---|---|
| レンダーpy | `render_<動画ID>_v<NN>_<変更概要slug>.py` | `render_0290_v32_ctafix.py` |
| 出力MP4 | `<案件命名規則に従う本体名>_v<NN>.mp4`（**pyと同一のv番号**） | `mov_ugc_0290_..._v32.mp4` |
| 中間素材 | `<動画ID>_v<NN>_<内容>.<ext>` または専用dir配下 | `0290_v32_slowclip_cut05.mp4` |
| 再生成音声 | `<動画ID>_<行ID or 内容>_take<N>.wav`（takeで採番、上書き禁止） | `0290_line08_take3.wav` |
| カットリスト | `cuts_<動画ID>_v<NN>.json` | `cuts_0181_05_v3.json` |

- **py ↔ MP4 のv番号は必ず一致**させる。「このMP4を再生成できるpyはどれか」が名前だけで一意に引けること。
- pyのslugは変更内容が分かる最短語（`ctafix` / `retime53` / `facecrop_c04` 等）。
- 1つのpyが複数動画を出す場合（バッチ）は `render_batch_<日付>_v<NN>.py` とし、**py内に出力対象の動画ID一覧をコメントで明記**する。

### 2.1 レンダーpyのdocstringヘッダ（必須・2026-08-10 追加）

レンダーpyは**冒頭のモジュールdocstringに「変更内容」「変更理由」を必ず書く**。
py自身が修正記録の一次資料になり、Notion行の起票（notion_log_render.py）もここから引ける。
ファイル名のslugだけでは「なぜ」が残らず、後から却下理由・回帰チェックの照合ができない。

```python
\"\"\"render_0290_v32_ctafix.py
対象: 0290（バッチなら動画ID一覧）
前版: v30
変更内容: CTA音声の重複を除去、BGM二重化を解消
変更理由: 2026-07-10 クライアント指摘「CTAで音が二重に聞こえる」（原文引用）
検証方法: 全フレーム48分割目視＋実聴
\"\"\"
```

- 「変更内容」「変更理由」の2語を含むdocstringが無いpyは `check_adoption_sync.py` の検査[G]が指摘する。
- ★**遡及しない**（`notion-db-contract.md` §10「過去案件には遡及強制しない・新規からFAIL適用」と同じ扱い）。
  既定は**規約制定日(2026-08-10)より新しいpyだけFAIL、それ以前はWARN**。
  過去案件の納品ゲートをこの規約で赤くしない（納品を止める理由として不適切）。

  | 指定 | 挙動 | 使うとき |
  |---|---|---|
  | （既定） | 制定日以降のpy=FAIL / 以前=WARN | 通常。既存案件も新規案件もこれでよい |
  | `--legacy-py-ok` | 全pyをWARN | mtimeがコピー等で新しくなった旧py群を一時的に通す |
  | `--strict-py` | 全pyをFAIL | 案件の全pyを規約準拠にし終えた後、その状態を維持する |

  判定は mtime なので厳密な作成日ではない（コピーで新しくなる＝安全側にFAILへ倒れる）。
- ユーザー指摘が理由の場合は**原文引用**で書く（要約は解釈違いの温床）。

## 3. ディレクトリ規約（修正・量産案件レイアウト）

制作系（参考分析→新規制作）は `file-structure.md`（in/work/out）に従う。**修正・バリアント量産**は以下を標準とする（`scripts/new_revision_project.py` でスカフォールド）:

```
<project-root>/
  ledger.md            ← ローカル修正台帳（§5の書式。Notionが正、これは作業中のミラー/下書き）
                         ★ユーザーが指示を書くのはNotion側の修正台帳（`REVISION-LEDGER.md`）。
                           このファイルに指示を書かせない
  sources/             ← 元素材（read-only扱い。ここのファイルは編集も削除もしない）
  vo/                  ← VO・再生成音声（take付番、上書き禁止）
  bgm/                 ← BGM素材（頭出し情報をledgerに記録）
  cta/                 ← CTAカード・モックアップ・矢印等の固定オーバーレイ素材
  intermediates/       ← スロー化・holdpad・パリンドローム等の中間素材（消さない。一度問題を解決した中間素材は次の修正で再利用できる）
  renders/             ← 全レンダー出力（全v保持。削除禁止）
    <動画ID>/          ← 動画ごとにサブディレクトリ
  py/                  ← 全レンダーpy（全v保持。削除禁止）
  qa/                  ← 検品証跡（抽出フレーム・音声実測ログ・比較画像）
    <動画ID>_v<NN>/
  delivery/            ← 納品コピー先（§6: cp -n で新規コピーのみ、上書き禁止）
```

- **iCloud/同期フォルダ直下でレンダーしない**（I/Oハング）。ローカル作業領域でレンダーし、最後に外部SSD/納品先へコピー。
- 外部SSDへ直接書く場合も上書き禁止は維持。

## 4. 更新トリガー（いつ管理DBを書くか）

**「採用が動いた瞬間」に即時更新。後回し・まとめて後で、は禁止。**

| イベント | 更新するDB | 書く内容 |
|---|---|---|
| レンダー完了（採否問わず） | レンダーpy管理DB | 出力MP4パス・pyパス・中間素材パス・音声/BGMソース・採用/不採用 |
| 検品完了 | QAログDB | 対象秒数・QA種別・結果・確認内容・証跡パス（qa/配下） |
| **採用py/MP4/vの確定・変更** | **レンダー行+動画台帳relation（即時・2操作）** | ①レンダー行の`採用状態`フリップ（新採用→採用、旧採用行→旧採用） ②動画台帳の`採用レンダー`relation差し替え。台帳の採用セル（鏡）と§5履歴文は`notion_autolink.py --apply`が生成（手打ちしない。notion-db-contract.md §2） |
| 修正指示の状態変化 | 修正指示DB | ステータス更新（行の削除は禁止。履歴として残す） |
| ユーザー承認・納品 | 動画台帳＋修正指示DB | 採用確定＋ステータス=納品済み |

- **管理DB未更新のまま「完了」と報告してはならない**（違反は重大な作業規律違反）。
- **着手前に必ず動画台帳で現採用を再確認**してから触る。会話だけを根拠に着手しない。
- 採用pyは「詳細py未確認」等の曖昧記述を残さない。見つかるまで調べてフルパスで書く。

## 5. 履歴追記の書式（上書き消去 厳禁）

過去の採用値・却下vと理由・判断根拠を消さない。動画台帳の本文（またはローカルledger.mdの当該動画セクション）へ**日付付きで追記**する。書式:

```
YYYY-MM-DD: v<NN>採用 ← v<MM>却下(<却下理由>)。根拠=<判断根拠>。py=render_<vid>_v<NN>_<slug>.py
```

実例:
```
2026-07-10: v32採用 ← v30却下(BGM二重化・CTA音声重複)。根拠=全フレーム48分割目視+実聴+クライアント承認。py=render_0290_v32_ctafix.py
2026-07-10: v30却下のまま保全(delivery/に残置。「v30は使わない、v32を使う」)
```

- 判断根拠の語彙: 全フレームSSIM／48分割(1秒48フレーム相当)目視／32分割目視／尺実測／ラウドネス実測／クライアント承認／ユーザー承認 等、**実測・承認ベース**で書く（「良さそうだったから」は根拠ではない）。
- 却下したvも「なぜ却下か」を必ず残す（同じ轍を踏まない材料）。

## 6. 納品規約

1. **納品フォルダへは新規コピーのみ**: `cp -n`（no-clobber）等で上書きを機械的に防止。既存納品物を置き換えず、新しいファイル名で追加する。
2. **採用版を明記**: vが複数納品フォルダに残る場合は「v30は使わない、v32を使う」まで、納品連絡とledger/動画台帳の両方に書く。
3. **本数・保存先の自己検算**: 納品前に個数を数え（`ls | wc -l` と指示本数の突合）、指定パスを一字一句確認する。
4. **納品前に §7 の機械検算を必ず通す**。

## 7. 機械検算（意思ルールに頼らない強制機構）

| スクリプト | 用途 | 実行タイミング |
|---|---|---|
| `scripts/notion_gate.py` | **納品前必須ゲート**: export(adopted/renders自動生成)→autolink --apply→audit→check_adoption_sync[A]-[G]→**check_variant_dupes**を直列実行し、PASS/FAILをプロジェクト台帳へスタンプ。`--light`=作業中の簡易ゲート(読み取りのみ・スタンプなし。**lightのPASSは納品可ではない**) | **納品前・「完了」報告前に必須**(単独実行を置換)。lightは作業中いつでも |
| `scripts/check_adoption_sync.py` | ローカルのpy/MP4の最新v・対応関係と、管理DBの採用v/全レンダー行を突合([A]-[G]。[F]=却下版の行登録漏れ・[G]=pyのdocstringヘッダ欠落 §2.1) | ゲート内で自動(単独実行も可) |
| `scripts/check_variant_dupes.py` | カットリストJSONから ①同一動画内の素材重複 ②バリアント間のカット位置ごと素材重複 ③バッチ横断の使い回し上限超過 を機械チェック | バリアント設計後・レンダー前・**ゲート内で自動**(`notion_gate.py --cutlist <JSON>`) |

★`--cutlist` を渡さないと素材重複は検査できない。**未指定は結果に `check_variant_dupes=SKIP(--cutlist未指定)` と明示され、スタンプにも残る**（黙って省いたことにしない）。カットリストがある案件では必ず渡す。
| `scripts/notion_ingest_cutlist.py` | カットリストJSON→カット台帳・素材使用DB・テロップチェックDBへ一括機械起票(冪等・手転記廃止) | ビルド確定後 |
| `scripts/notion_log_render.py` | レンダー行+QAログ行の機械起票(却下版も1レンダー=1行) | **レンダーするたび** |
| `scripts/notion_autolink.py` | テキストキー→relation・鏡列・§5履歴行の機械生成(rollback_log付き) | セッション終了時+ゲート内 |
| `scripts/notion_audit.py` | 契約§8不変条件の読取専用監査 | ゲート内(単独も可) |
| `scripts/notion_rollback.py` | rollback_log.jsonlの逆適用(層3ロールバック) | 事故時 |

Notion DB群のキー文法・Write Contract・語彙・不変条件の単一規範は `notion-db-contract.md`。

- 人間の目視・フォークの自己申告・外部AI検証のいずれも見逃した重複を、機械チェックだけが検出した実績あり（VERARUS 0181_04 cut03）。**機械チェックは省略しない**。
- N件処理でツール呼び出し回数がNより著しく少ない報告は個別検証が行われていないシグナル（PRINCIPLES §2）。

## 8. 修正作業の不可侵ルール（20条の要約。全文は各案件の revision-workflow スキル）

- pyを必ず残す／完成MP4を直接編集しない／上書きしない／過去修正を戻さない（新修正前に差分表を作り、1箇所直すたび回帰チェック）
- 該当カットだけ触る（全体クロップ・全体音声差替・全体BGM変更は原則禁止）
- BGM入りMP4音声を流用しない（VO単体+共通BGM頭出しで再ミックス）
- 音声違和感が2回続いたら編集で粘らず再生成（声質モデルは案件指定に固定）
- 修正対象外を「良さそうだから」で勝手に最適化しない。依頼された修正だけを閉じた差分で入れる
