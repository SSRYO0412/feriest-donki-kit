# 台本→素材選定・検証プロトコル（SELECTION_PROTOCOL）

> 正本: `~/.claude/skills/_video-core/selection/references/SELECTION_PROTOCOL.md`（sync_core.sh で配布）。
> 台本（言語）から映像素材（視覚）へのマッチング作業全般に適用する案件非依存プロトコル。
> 案件V 30本量産バッチ（2026-07-01〜02）の全事故分析から一般化。**商品・素材・フック固有の知識を含まない**。
> 案件固有のデータ（合格基準表の具体値・輝度閾値・検証済みクリップ台帳）は案件スキル側に持ち、本書の手順で**導出・更新**する。

## 0. 六つの普遍原則（商品・素材・フックに依存しない）

1. **presence ≠ persuasion**: 「映っている」は合格条件ではない。「その1フレームから第三者が主張を言い当てられる」が合格条件。
2. **主張と映像の一致 > 画の綺麗さ**: どれほど良い画でも主張の証明になっていなければNO-GO。
3. **判定は誘導なしブラインドで**: 「このカットは○○に合っているか?」と聞いた時点で判定は汚染される。テロップを伏せて印象を自由記述させ、期待訴求が自発的に出るかで判定する。
4. **動きの主張は動きで判定**: 静止フレームは動作の証明に使えない（GO判定の根拠にできるのは動画切り出し/フレーム差分のみ。静止フレームは不合格判定の根拠にしかならない）。
5. **選定は相対評価**: 単独絶対評価は「まあ映ってるしOK」を通す。候補2つ以上を並べて選ぶ。
6. **閾値・条件は実測から導き、追記型で成長させる**: 頭で決めた閾値ではなく、良い/悪い実例のフレーム実測から取る。

## 0.5 「差し替え」フェーズ固有の原則（案件S 2605/Dec28 の全指摘から・2026-08-04追加）

初回選定が終わったあと、ユーザーの指摘で1カットずつ差し替える段階には別の失敗様式がある。

1. **差し替えは芋づるで重複を生む**。あるカットをXに替えたら、既にXを使っていた別カットと
   同一クリップになる（実例: S20をC1374にしたら S19 と同一クリップになり「次のカットと全く同じ絵」）。
   **1本差し替えるたびに使用クリップ名の重複を機械で数える**。
2. **隣接カットの被りは画素差で検算できる**。差し替え後に前後カットの平均画素差を測り、
   25未満なら似すぎ（実測: 別カットなら55〜65、同一クリップだと10未満）。
3. **意味が同じ＝同じ動作**まで具体化して探す。「0618の素材に変更」のような指示でも、
   置き換え先は**現行カットと同じ動作**（洗面台で肌を触る／頬になじませる／手のひらに注ぐ）で選ぶ。
4. **1カットの指摘は前後3カットの点検を伴う**。1つ直すと流れの中での役割が変わる。
5. **却下した版と理由を必ず残す**。ユーザーが「さっきの方が良かった」と戻すことがある
   （実例: 分割画面を 寄り→引き→引き調整→寄りに復帰。履歴が無いと同じ試行を繰り返す）。
6. **「引けば分かる」は誤り**。商品を見せたくて引くと、何をしているか却って読めなくなることがある。
   寄り引きは必ず両方作って並べる（実例: 分割画面は顔の寄りの方が「マスクを貼っている」と伝わった）。
7. **表情の指定は最優先で拾う**。「不満優先」「ちゃんと演者が写っている」「化粧品を使っている」等は
   構図一致より優先されることがある。妥協した場合は台帳に残課題として明記する。

## 0.6 素材DBの使い方の注意（2026-08-04追加）

- **説明文の全文検索は否定文を拾う**。「塗る・開ける動作は確認できない」が「塗る」でヒットする。
  キーワード検索は候補の絞り込みまで。合否は `demo_flag` と `demo_note` の読解＋実フレームで決める。
- **`demo_flag=1`（実演あり）で絞ると候補が現実的な数になる**（実例: 1141窓→457窓→数十本）。
- **DBの説明は検索の索引であって合否の根拠ではない**（`description` が動作語を含んでいても
  実際は静止接触のことがある、という既知の罠と同じ）。
- **尺は確定窓の長さで判定する**。隣接窓が連続していれば繋げて使える。
- **指定フォルダがある場合は全窓を機械で走査してから目視**する。「無い」と言う前に全数を見る。

## 1. 標準フロー（この順序を崩さない）

```
① 台本の各行を意味カテゴリに分類
② カテゴリ別合格基準表を「作業前に」文書化（作業中の恣意的緩和は禁止）
③ 検証済みタイムスタンプ台帳（verified_clips）を引く ← DB検索より先
④ 台帳に無い/使い切った場合のみ素材DBを検索（候補は複数出す）
⑤ 候補ごとに提案in点の複数フレームを抽出し、1枚ずつ個別に目視（montage禁止）
⑥ 自己判定 + 外部AI独立判定の二重検証。両方GOで初めて採用
⑦ NO-GOなら外部AIにDB再探索させ代替候補→⑤へ戻る（両GOまで反復）
⑧ 採用結果・判定を台帳へ追記（台帳は追記型で成長させる）
```

- **⑤の目視を経ずに次のカットへ進むことは禁止**。Nカットあるなら N回この確認を行う（ツール呼び出し回数がNを大きく下回る作業報告は個別検証が行われていない強いシグナル）。
- 素材が見つからない場合、**案件ルールで禁止された解決策（追加撮影等）を提案しない**。「まだ探していない候補がないか」（フィルタ解除・全量再検索・同一ファイル内の別タイムスタンプ・別フォルダ）を優先し、それでも無ければ「次点レベルで確定」として報告に明記する。

## 2. ①意味カテゴリ分類と ②合格基準表の作り方

台本の一文は「何についての話か（テーマ）」と「画面に何が映っているべきか（具体的な視覚的事実）」の2層を持つ。判定は常に**アクション一致**（後者）で行う。

**主張タイプ分類表**（新しいフック・訴求はまずここに分類する。タイプが伝達条件の既定値を決める）:

| 主張タイプ | 例 | 既定の伝達条件 | 既定の証明形態 |
|---|---|---|---|
| 質感・材質 | マットな質感/レザー/生地の張り | 解像する接写+斜め光+輝度ガード（実測キャリブレーション） | 表面のディテールが読める1フレーム |
| 色・見た目 | 深い色/発色 | 白飛び・黒潰れ・フラット画の排除（輝度ガード） | 色が正しく再現された順光フレーム |
| 機能・構造 | 高さ/防水/クッション/軽さ | **機能が作動している直接証明のみ**。間接ショット（裏側・縁・部品単体）は不可 | 実使用ショット（乗る/沈む/弾く/浮く）or 断面・比較並置 |
| 動作反応 | 押すと戻る/なぞると止まる/曲がる | 動画/フレーム差分で動きを判定（静止フレーム禁止） | 変形〜復帰が連続フレームで読める区間 |
| 不在証明 | ロゴがない/縫い目がない | 対象範囲**全体**を静止提示≥1秒（部分提示は証明にならない） | 全周・全面が一望できるホールド |
| 社会的評価 | 高見え/褒められる | 文脈（服・背景・場）のpremium度。生活感ノイズ排除 | スタイリング込みの整った引き |
| ブランド・情緒 | オーラ/正体は○○/開けた瞬間 | 明るい実写+ブランド文脈（箱/人物/空間）。AI生成・無機質背景は不可 | テロップの瞬間と映像の瞬間の一致（開封なら開封中） |
| 抽象概念 | 質で選ぶ/もう戻れない | **代替可能カテゴリを事前に明文化**してから運用（現場判断に任せない）。語感（速さ/落ち着き/自信/軽さ）に近いモーションを優先 | 前後カットと同系統の質感/動作カット（同一動画内の既出素材は不可） |

- 複合フックは複数タイプの条件をAND。
- 案件開始時に、この表を雛形に**案件別の合格/不合格の具体例つき基準表**を作ってから選定に入る（実測例が溜まるたび追記）。

## 3. ⑤フレーム目視の作法

- カットの尺全体を **0.3〜0.5秒間隔で最低3〜5枚** 抽出（`ffmpeg -ss <t> -i <src> -frames:v 1`）。動作系は動作の開始・中間・終了が収まるように。
- **1枚ずつ個別にReadで開く**。montage/コンタクトシートでの合否判定は禁止（内部トリアージには可）。
- 動作カテゴリは静止フレームでGOを出さない: (a) 候補区間2〜3秒を低解像度mp4/GIFに切り出す、または (b) フレーム差分（`ffmpeg -i in.mp4 -vf "tblend=all_mode=difference" diff.mp4`）で「どこが動いたか」を可視化してから判定。「手の位置がフレーム間で変化しているか」を具体的に確認し、変化がなければ即NO-GO。
- **DBのdescriptionを信用しきらない**: descriptionは「クリップ内の一部シーンの描写」であり、指定in点の実際の絵とは限らない。descriptionに動作語（なぞる/押す等）があっても実際は静止接触のケースが複数実証されている。
- **「不合格」はそのファイルではなく特定のtimestamp窓に対する判定**。過去のNO-GO記録を見つけても、別タイムスタンプでの再検証を試みてから除外する（数十秒の尺があれば区間ごとに動作は全く変わる）。逆に過去の「GOOD」記録も再使用時は自分の目で再確認する。
- 顔・写り込みルールがある案件では、フォルダ名・DB列を目安にせず**該当in点のフレームで実確認**。in点を数秒ずらすだけで写り込みが画角外になることも多い（クリップ丸ごと不採用の前に窓移動を試す）。

## 4. ⑥二重検証（自己判定+外部AI独立判定）

1. 自己判定: 抽出した複数フレームを1枚ずつ開き、フレーム間の変化を見比べ、基準表に照らしてpass/fail。
2. 外部AI判定（Codex等）: **フレーム画像のファイルパスをそのまま列挙し、workingDirectoryを設定して外部AI自身に全フレームを直接開かせる**（要約を経由させると精度が大きく落ちる）。promptには当該カットのテロップだけでなく**動画全体の台本の並び**と**基準表全文**を含める。「全フレームを開いて、フレーム間の変化から動作の有無を判断せよ」と明示。
3. **両方passで初めてGO**。どちらか一方でもfailならNO-GO→代替探索。
4. 外部AI呼び出しは **1回=3〜5カットに分割**（長大バッチは接続断で完走しない実績）。部分回答しか得られなかった場合、得られた指摘は正直に採用し、未回答分は自己判定で代替した旨を報告に明記。
5. 判定はnon-deterministic（複数回で微妙にブレる）。疑わしい場合は複数回・複数フレームで確認。
6. **制作フォークと検証フォークを分離**し、検証には「合格のはず」という文脈を与えず「落とす理由を探せ」の敵対的プロンプトのみで依頼。**納品前の最終監査（ゼロ重複の機械チェック+リスクカットの生フレーム目視）は必ず親セッションが自分で行う**（フォークの「複数フレーム確認済み」自己申告が事実と異なっていた実績多数）。

## 5. フック伝達力検証（訴求の核になるカットに必須）

**(a) キャプションブラインド判定**: テロップを見せずにフレームだけ渡し「この画の印象を形容詞3〜5個で」と聞く。期待訴求が**自発的に出てこなければNO-GO**。自己判定も同手順。

**(b) 数値ガード（輝度等）**: 測定コマンド:
```bash
ffprobe -v quiet -f lavfi "movie=<frame.png>,signalstats" \
  -show_entries frame_tags=lavfi.signalstats.YAVG,lavfi.signalstats.YLOW,lavfi.signalstats.YHIGH -of json
```
- 閾値は案件ごとに**再キャリブレーション必須**: 最初に合格させた5〜10フレームを実測し、その分布からガード値を取る（照明環境・商品色に依存。他案件の閾値を流用しない）。
- **測定対象は「実際に使用するカット窓（tin〜tin+dur）の中央フレーム」**。ソース素材の別タイムスタンプの明るいフレームで測って合格させるのは無効。納品後の最終監査でも**納品ファイルから抽出したフレームで再測定**。
- 数値ガードで検出できない失敗モードがある（直射日光の白飛び+硬い影は輝度正常域に入る）→ ブラインド判定と目視で担保。
- ユーザーが明示承認した素材は数値ガードの適用除外にできる（**素材特定はユーザー原文パス・現物確認を最優先。実測値だけで推定断定しない**）。

**(c) 相対評価**: フックカットは候補を必ず2つ以上並べて「どちらが伝わるか」で選ぶ。(a)(b)を両方通った候補が1つしかない場合のみ単独採用可。

**(d) 納品水準を分ける5要因**（goodcase/惜しい実測分析より。選定時に1つずつYES/NOで採点し、NOが1つでもあれば代替を探してから妥協）:
1. 決めカット（ブランド開示/ヒーロー）は「明るい実写+ブランド文脈」
2. 主張と映像の一致が最優先（間接ショットで機能主張を代替しない）
3. 動作は「見えている」こと（触れているだけはNG）
4. 生活感ノイズと照明の排除（背景・服・光も採点対象）
5. 主役占有率（引きカットは1本に1〜2箇所に限定）

## 6. 台帳（verified_clips）運用

- スキーマ: `verified_clips.template.json`（本ディレクトリ）。**rel + timestamp窓**単位で verdict（GO/CONDITIONAL/WEAK/NO-GO/BANNED/USED-UNREVIEWED）・used_in・quality_signal・hook_strength・顔/権利リスクを記録。
- **追記専用（append-only）**。素材選定は必ず (1)台帳 → (2)DB検索 の順。新候補が検証を通ったら台帳へ追記。
- 新素材バッチ・別商品はセクションを分けて追記（スキーマ共通・relの名前空間だけ変わる）。既存の正典は上書きしない。
- 禁止素材（BANNED）・顔リスクは最初のスクリーニング時に必ず埋める（後から発覚した禁止事項は即時追記）。
- hook_strength: フック名→strong/weak。フックカット選定はstrong最優先、weakは「そのフックには使わない」の意味（他用途は妨げない）。

## 7. 素材DBクエリ集の整備

DB構築後、案件ごとに `asset-db-queries.template.md` を雛形にクエリ集を作る（スキーマ説明・用途別キーワード早見表・使用済みID除外・既知の罠）。DB検索の注意:
- 候補が枯渇したカテゴリは、まず絞り込みフィルタ（向き・カテゴリ等）を外して**全量再検索**するのが最優先の一手。
- 向き（orientation）等のメタ列は撮影機材のローテーションメタデータを反映しないことがある。列値だけで採否を決めず、必ずフレームを1枚抽出して実確認。
