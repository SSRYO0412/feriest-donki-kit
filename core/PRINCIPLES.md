# 動画・音声制作スキル 横断原則（PRINCIPLES）

> 全ての動画/音声制作スキル（reference-video-clone 系・faceless 系・swap 系・案件V・viral/jp-buzz・audio-emotion-voice-clone）に共通する原則。
> 各スキルの SKILL.md に書かれた個別ルールが本書と重複するのは正常（自己完結性のため）。**矛盾したら各スキルの SKILL.md / 専用ルール（例: BEFOREAFTER_RULES.md）が優先**。
> 正本: `~/.claude/skills/_video-core/PRINCIPLES.md`（各スキルへは sync_core.sh で配布）。

## 1. 実測主義（記憶・経験則で数値を置かない）
- 数値・仕様（色/位置/サイズ/尺/セーフゾーン/タイミング/閾値）は必ず **(a) 対象そのものからの実測**（フレーム抽出・ピクセル計測・波形/ffprobe）または **(b) 公式一次情報** で決める。「一般的にこのくらい」は根拠ではない。
- 値を再指摘されたら微調整でなく**根拠そのものを一次情報まで遡って作り直す**。
- 閾値（輝度ガード等）は頭で決めず、良い/悪い実例のフレーム実測から導き、**追記型で更新**する。
- 参考が変われば数値は再測定。**再利用してよいのは手順と語彙の枠だけ**。

## 2. サブエージェント/外部AI検証の鉄則
- **サブエージェントの合否報告を鵜呑みにしない**。偽陽性（誤りを見逃す）・偽陰性（在るものを無いと言う）の両方の実績がある。所見は実測（測色/MAE/ffprobe）＋**親の直接 Read 目視**でクロスチェックしてから採否を決める。
- **制作担当と監査担当を分ける**。並列実行する時は、作るサブエージェントと、作ったものを落とす理由を探す敵対レビューサブエージェントを別に置く。監査担当には制作側の自己評価を根拠にさせず、参考/制作指示/訂正指示/実ファイルだけを見せる。
- **監査サブエージェントの監視も行う**。監査担当が全対象を見た証拠（対象リスト、見たファイル名、問題箇所、未確認項目）を出さない場合、その監査結果は無効扱いにする。必要なら別サブエージェントに「監査漏れ・論理飛躍・自己正当化」を敵対レビューさせる。
- **親エージェントの最終責任を移譲しない**。制作担当・監査担当・監査の監視担当の報告は、すべて「仮説」扱い。納品前に親エージェントが必ず制作指示・訂正指示・参考素材・3周検品結果を自分の目で突き合わせ、全項目PASSでなければ納品しない。
- 依頼プロンプトに「過去の失敗パターン例」を具体的に書きすぎない（そのパターンに当てはめる**確証バイアス**を誘発する）。中立的な「客観的に記述せよ」に留める。
- 1体に100枚超の連続 Read を背負わせない（後半で要約に劣化する）。**区間分割して並列**にする。
- N件処理でツール呼び出し回数がNより著しく少なければ、個別検証が行われていない強いシグナル。**期待呼び出し回数の下限を見積もってから任せ、下回ったら結果を疑う**。
- vision 並列でレート制限（"Server is temporarily limiting requests"）が出たら、その判定は**「不合格」ではなく「無効」**。決定論ツール＋自分の目視に切り替える。
- 制作した本人による検証は甘くなる。**検証は文脈を与えない敵対的プロンプト（「落とす理由を探せ」）で別フォーク/Codex に依頼**し、納品前の最終監査は必ず親が自分の目で行う。

## 3. 目視の作法
- **Claude 自身が Read ツールで画像/フレームを直接開いて見る**。「スクリプトを走らせた＝確認完了」は禁止。数値（MAE等）はトリアージであり、合否の最終判定は目視。
- **ユーザーへの提示・保存は個別ファイルのみ。montage/コンタクトシートでの提示は禁止**（細部が潰れて見落とす）。内部トリアージ用の contact sheet / compare_grid は可。
- 生成動画は**参考との全フレーム横並び照合**（1秒48分割基準＝ネイティブフレームを一切間引かない全数）。疎なサンプリングは「静止」と「低速移動」の区別すら誤る（実証済み）。
- 「不合格」判定は**そのファイルではなく特定の timestamp 窓**に対するもの。別窓での再検証を試みてから除外する。

## 4. 多重サンプリングと測定の罠
- 色/SE/サイズ等の実測値は **N≥3 で確定・2手法一致**（機械測定＋tight crop 目視）。1サンプル/1手法で確定しない。
- 既知の混入源: 被写体の帽子（オレンジ）・木目壁・プラットフォームUI・前テロップの残像・BGM（SE誤検出）・白パネル上の濃色文字。反例スキャンを能動的に行う。
- 動作カテゴリ（なぞる/押す等）は静止フレームで GO 判定しない。**動画切り出し or フレーム差分で「動き」そのもの**を判定する。

## 5. 主張と映像の一致（具体性の原則）
- 「テーマ一致」と「アクション一致」は別物。**台本の行が指示する具体的動作・状態が画面に文字通り映っているか**で判定する。presence ≠ persuasion＝「映っている」でなく「その1フレームから第三者が主張を言い当てられるか」。
- 判定は誘導なしブラインドで（「このカットは○○に合うか?」と聞いた時点で汚染）。テロップを伏せて印象を自由記述させ、期待訴求が自発的に出るかで判定。
- 素材選定は**相対評価**（候補2つ以上を並べて選ぶ）。単独絶対評価は「まあ映ってるしOK」を通す。
- 判定基準は**作業前に文書化**し、作業中に恣意的に緩めない。

## 6. 閉ループ候補選別（耳/目の印象で選ばない）
- 生成は確率的。「見て/聴いて→直して」はランダムウォーク。**元素材から数値目標を実測 → K候補生成 → 目標とのL2距離で機械選別 → 外れた行/カットだけ条件を変えて再生成**。
- 「なんか変」は必ず数値化できる（ギャップ構造・F0オフセット・彩度・カデンスのズレ等）。逆QA＝生成物を元と同じ計測で突き合わせ、系統誤差を見つける。
- ただし数値が良くても知覚品質は別（PSOLA輪郭移植の教訓）。機械選別の後に必ず目視/試聴ゲート。

## 7. 環境・並列の安全策
- 重い ffmpeg/レンダー/生成は **iCloud 外**（`~/faceless-work/`・`~/render-engine/`・中間は `/tmp`）。`~/Documents`/`~/Desktop` は同期退避で I/O がハング。
- Remotion は node@22（`/opt/homebrew/opt/node@22/bin` を PATH 前置）。
- codex 画像生成の並列は**専用 cwd（`-C /tmp/xx_<名前>`）で実行し自分の cwd のファイルだけ拾う**（共有フォルダの「最新コピー」はレースで取り違え）。同時数 gen≈5 / fal swap≈9（swap は `--out` 固有パスでレース無し）。
- バッチは **skip-if-exists（レジューム）＋失敗隔離**（1本の失敗で全体を止めない）。成果物名には一意な識別子（ジョブID）を必ず含める。
- Workflow ツールの `args` は JSON 文字列のまま渡ることがある → `const ARGS = (typeof args === 'string') ? JSON.parse(args) : args` の防御パース＋実行後に背骨/出力の非空検証。

## 8. 承認ゲート
- **課金を伴う実行**（fal swap/i2v、大量生成）・**カット/プロット選定**・**納品**の前にユーザー承認。`--dry-run` で件数/payload を確認してから本番。
- 失敗/リトライも課金される。短尺で数本試写→本番。
- エンジン（コード/アセット）が存在する≠使われている。**5次元それぞれ、案件の edl.json / props に実際に値が authoring されているか**を毎回確認する。
- 境界（カット点 in/out・分割点）は必ず実測した単語/文節境界にスナップ。目分量・キリのいい秒数で置かない。
- 外部アプリの非公開内部フォーマットは推測復元しない（確実に制御できる手段へ切替）。前提（素材の本数/型の同一性等）が曖昧なら決め付けず AskUserQuestion。

## 9. 検証は満点まで反復
- 部分合格・「だいたいOK」は不可。全層・全項目 PASS（WARN/FAILゼロ）まで検証→修正→再検証をラウンド上限なしで繰り返す。
- 検証結果は毎ラウンド記録し、何が直って何が残っているかを明示（「変化なし」の曖昧報告をしない）。
- 同じ箇所が連続で割れる場合のみ、原因（測定ノイズ/実バリエーション/設計ミス）をユーザーに報告して方針確認。

## 10. テンポ・パリティ（時間軸の完コピ）
- 完コピ対象は静的な見た目（色/フォント/位置）だけでなく**時間軸の編集量**: カット密度（cuts/min・ショット長中央値・最長ショット）・SE密度（SE/分）・テロップ更新頻度（遷移/分）・発話密度（語/秒・変速）。出力は参考と**数値照合（±30%目安）してから納品**する（RVC系は `verify_tempo.py`）。静的一致でもテンポ乖離は「編集されていない」印象で差し戻される（実証: カット/分1/5・31秒ノーカット・SE 6発vs28発でクライアント差し戻し。合格した手動編集版は全指標±35%以内だった）。
- **単一閾値のショット検出を信じない**。トーキングヘッドのジャンプカットは scene 0.30 で4割取りこぼす（実測 19 vs 32カット）。複数閾値スイープ（0.30,0.12）でカット数が多い方を採用し、乖離が大きければ低閾値側の誤検出を目視除外。
- **分析で測った数値は、設計（EDL/スペック）に変換されて初めて意味を持つ**。「分析は語彙を知っていたが設計で捨てられた」ドロップが実敗因になった。設計直後に自分の設計値（クリップ数/分・SE数/分）を参考実測と数値比較するセルフチェックを挟む。
- **テロップは参考ごとに形態が別物**。過去案件・テンプレ既定の様式を持ち込まず、毎回全要素（デザイン/サイズ・位置/タイミング/改行・意味単位の表示/入り方・逐次行・縮退・残留などの動的様式）を参考と**同ビートの横並びフレーム目視**で照合し、識別不能になるまで反復（フォント完全一致原則の全要素拡張）。**「入り方」等の動的要素は静止画でなくフレーム列（動き）で照合する**（スチル一致のみで提出→「入り方が違う」差し戻しの実証あり）。
- **★統計パリティは落第検出専用の必要条件であり、合格条件ではない（Goodhart警告）**。指標を通すための演出（例: カット検出数値を上げるための機械的ズーム交互）は、全数値PASSのまま「機械が編集した」出力を生む（差し戻し実証）。合格判定は**知覚ゲート**でのみ出す: 全カット境界・全テロップ出現をフレーム列＋音声で1箇所ずつ検分し、通し視聴で違和感ゼロまで反復。編集判断は集計値でなく**判断文法**（正解編集の全カット・全テロップを「状況→判断」として数値付きでログ化した移植可能な文法）に従う。

## 11. 資産の育て方
- 検証済みの実測知見（クリップの GO/NO-GO、トーン語彙、フック強度、閾値）は**追記型の台帳/ライブラリ**（verified_clips.json / tone-library.md / negative-prompt-library.md）に集約し、次回は台帳→DB検索の順で引く。過去の「GOOD」記録も再使用時は自分の目で再確認。
- スキルの共通ファイルを改善したら `_video-core` へ `sync_core.sh pull` で回収し、`push` で家系全体へ配布する（ドリフト防止）。
- 案件非依存の運用正本（2026-07-11 追加）: **版管理・履歴保全=`revision/`（VERSIONING.md・チェックリスト・採用v突合/素材重複の機械検算）／台本→素材選定・検証=`selection/`（SELECTION_PROTOCOL.md・台帳テンプレ）／ffmpegコンピレーション編集=`compilation/`／VO再構築・話速/音量修正=`vo/`**。新案件はここから始め、案件スキルには固有数値・固有データだけを書く。

## 12. 編集ソフトを自動操作したら「書き出して画素で」確かめる（2026-08-01 追加）

**事件**: Premiere のテロップ46枚にアニメーションとエフェクトをスクリプトで付け、
APIで読み戻して「時刻も値も設計どおり」を80枚全数照合してPASSにし、レンダーまで出した。
ユーザーが完成MP4を見て「アニメーションとエフェクトが全部外れている」。**全く効いていなかった。**

**真因**: `property.addKey(t)` / `setValueAtKey(t, v)` の `t` は
**クリップの素材内の位置（inPoint）を基準にした秒**。
そして **Premiere の静止画クリップの inPoint は慣例で 3600.000秒（=1時間）**。

    clip.inPoint.seconds  = 3600.000
    clip.outPoint.seconds = 3605.000

0.0〜0.3秒にキーを打つと**可視範囲より3600秒手前**に置かれ、
レンダラーは最後のキーの値を保持し続ける＝アニメーションが完全に無効になる。

**なぜ読み戻しで気づけなかったか**（ここが本質）:

    pr.getValueAtTime(0.0)    → -0.286   打った値。正しく見える
    pr.getValueAtTime(3600.0) →  0.5     実際に描画される値＝最終値の保持

`getKeys()` も `getValueAtTime(0.0)` も**自分が書いた座標系で返す**ので、
書き込みと読み出しが同じ誤りを共有し、照合は必ず通る。
**同じAPIで書いて同じAPIで読む検算は、座標系の誤りを原理的に検出できない。**

**正しい書き方**:

    var OFF = clip.inPoint.seconds;        // 静止画なら 3600.000
    pr.addKey(OFF + t);
    pr.setValueAtKey(OFF + t, v, true);

**必須の検算2段**:
1. 構造: `Math.abs(pr.getKeys()[0].seconds - clip.inPoint.seconds) < 0.01`（可視範囲の先頭にキーがあるか）
2. **実出力**: 書き出したMP4から、クリップ開始+0F〜+13F を抜いて**画素を測る**。
   変化がゼロなら効いていない。実例（型B=左からスライドイン、白文字の画素数）:
   - 壊れていた時: 23,525 → 23,713（ほぼ一定＝静止）
   - 直った後:     1,307 → 23,371（18倍に増加＝フェードイン）

**一般化**: 自動操作したパラメータは3層で確かめる。
**①スクリプトの戻り値 ②アプリからの読み戻し ③書き出した実ファイルの画素/波形**。
①②だけで「適用済み」と報告してはならない。①②が一致していても③が違うことがある。
とくに「配置（クリップ・尺・音）は正しいのに、アニメーション/エフェクトだけ効かない」時は、
**時間軸の基準（inPoint / シーケンス / ソース）を疑う**のが最短。

**関連する同種の罠**（すべて実際に踏んだ）:
- `component.remove()` は存在しない。キーフレームだけ消すと方向ブラーの適用量が残り**常時ボケる**。
  QE の `TrackItem.removeEffects()` で外す。
- QE の `getVideoTrackAt(t).numItems` は **Empty（空き）も数える**。
  `type==="Clip"` だけ集めてから添字を使わないと、エラーも出さず何も起きない。
- `app.project` は**手前のプロジェクト**を返し、作業中に入れ替わる。
  同名シーケンス（中身が空のものを含む）が別プロジェクトに在ることがある。
  **プロジェクト名＋シーケンス名＋クリップ枚数の3点で照合**する。
- 同じ .prproj を2重に開いたまま片方を保存すると、**もう片方の古い内容で上書きされて作業が消える**。

### ★3点照合は「書く」だけでは守られない。スクリプト冒頭で中断させる（2026-08-03 追加）

上に「3点で照合する」と書いてあったのに守らず、実害を出した（FERIEST案件）。
ユーザーが参考動画のプロジェクトを開いて確認した直後、`app.project` がそちらを指しているのに
気づかず作業を続け、**参考プロジェクトのSEを削除して書き出し、納品名で保存**した。
「SEは1本」「ナレーションは○○」と報告した内容は全部よそのプロジェクトのものだった。
（`saveAs` は別パスに書くので参考の原本は無傷だったが、成果物1本が丸ごと無駄になった）

**原則を散文で書くのをやめ、全スクリプトの冒頭に置く定型にする**:

```javascript
var p = app.project;
if (p.name.indexOf(WANT_PROJ) !== 0) return "★中断: 手前のプロジェクトが違う (" + p.name + ")";
var seq = null;
for (var i = 0; i < p.sequences.numSequences; i++)
    if (p.sequences[i].name === WANT_SEQ) { seq = p.sequences[i]; break; }
if (!seq) return "★中断: シーケンスが無い " + WANT_SEQ;
if (seq.videoTracks[0].clips.numItems !== WANT_V1) return "★中断: V1枚数違い";
```

**返り値で中断する**のが要点。警告を出して続行するのでは意味がない。
複数プロジェクトが開いていることは常態（実測で同時7本開いていた）。
`app.projects` を列挙すれば全部見えるので、迷ったら名前で特定してから作業する。

### ★プロジェクト項目を「名前」で探してはいけない（2026-08-03 追加）

版が変わってもファイル名は同じ（`T1_base.png`）。`children[i].name === "T1_base.png"` で
探すと、**前の版で取り込んだ項目**を掴む。実際に旧版のPNGが敷かれ、
ユーザーから「テロップが消えてる」と指摘された（旧版は該当行を別レイヤーに分離した絵だった）。

**必ず実ファイルのパスで照合する**:

```javascript
function findByPath(path, bin) {
    for (var i = 0; i < bin.children.numItems; i++) {
        var it = bin.children[i];
        if (it.type === ProjectItemType.BIN) { var r = findByPath(path, it); if (r) return r; }
        else { var mp = ""; try { mp = it.getMediaPath(); } catch (e) {} if (mp === path) return it; }
    }
    return null;
}
```

版ごとに出力ディレクトリを分ける運用（`telop_png_v07/`, `v08/`…）と必ずセットにする。
関連: `reference_premiere_clip_name_cache`（Premiereはクリップをファイル名で参照する罠）

### §13 最も安い決定的実験を最初にやる（2026-08-03 追加）

外部フォーマットを直接いじるとき、**「無改変で読んで書き戻したファイルは正常に開くか」**を
真っ先に確かめる。これを飛ばして複雑な改造を積み上げ、切り分けに何時間も溶かした。

一般形: **加工なしの往復（round-trip）が通ることを確認してから、加工を1段ずつ足す。**
壊れたら二分探索で加工を半分に減らす。1件→数件→全件で切り分ければ原因は必ず挟める。
（実例: 無改変=開ける / 1ノード追加=開ける / 1件分=開ける / 全14件=開けない → 原因を特定）

## §14 SEは「合成音」より「素材に写り込んだ本物」を探す（2026-08-06 楳図案件H公式PVで確立）

ホラー/体験型イベントの動画で、合成SEの「遠い悲鳴」を置いていたところ、
**撮影素材の中に本物の参加者の悲鳴が録れていた**。差し替えたら効きが桁違いだった。

### 探し方（78クリップから4本を発掘した手順）

全クリップの音声を0.25秒窓で解析し、以下の積で候補を出す。

```
RMSの突出（前後2秒の中央値比 > 2.2）
  × スペクトル重心 > 1200Hz
  × 1-4kHz帯のエネルギー比 > 0.28
  × 絶対音量 > -34dB
```

### 選別（ここを外すと会話やネタバレを掴む）

1. **F0を測る**。女性の悲鳴は500Hz超。`pitch_ceiling=1200` にしないと測れない
2. **文字起こしする → 空なら当たり**（言葉にならない声＝悲鳴）
3. ★**whisperは無音に近い音で幻聴を出す**（「ご視聴ありがとうございました」等）。
   転写だけで判定せず**有声率**も見る（息なら<25%）
4. **ネタバレ禁止語が入る候補は落とす**（実例:「水って何ですか?」← 仕掛けの核心語だった）
5. 切り出しは**窓の中で最大RMSの位置を探してから**。中心を決め打つと無音を掴む

### 使いどころ

- 山場の一撃に、合成のimpactと**重ねる**（本物の声が乗ると生々しさが出る）
- 「悲鳴より、沈黙が怖い」のようなコピーを書いたら、**実際に鳴らして直後に落とす**。
  BGMを `volume=0.30:enable='between(t,A,B)'` でダッキングして本当に静かにする。
  実測: 900-4000Hz比が 中盤0.008 → 悲鳴0.543 → 沈黙0.005

### 本人の「息」も同じ発想で採れる

TTSナレーションが「AIっぽい」とき、**話者本人の実録音から息継ぎを切り出して発話の直前に重ねる**と
聴感が大きく変わる。TTSが絶対に生成しない要素だから効く。

- 検出: 0.05秒窓で 無声(voiced<0.15) × 中庸の音量 × 高域比>0.28 × 長さ0.15-0.55秒
- ★**TTSの出力自体は加工しない。別トラックで重ねる**（出力をいじると声色が劣化する）
- 冒頭を「息 → 言葉」の順にすると、人間の発話パターンになる

> 声そのものの作り込み（register診断・話速の緩急・音量の弧・読み合わせ検証）は
> `audio-emotion-voice-clone` の「TTSナレーションが『AIっぽい』ときの診断と対処」を見る。

## §15 案件文書が先 — HANDOFF を読まずに着手しない（2026-08-03 Feriest で確立）

**事件**: 案件の `HANDOFF.md` に「[1]〜[3] は完了済み」「フォントは比較レンダーの上で
採用決定・入手済み」と書いてあったのに読まずに着手し、**完了済み工程を丸ごと再実施**し、
採用決定済みのマーカー体を「無い」と誤断定して**丸ゴシックに差し替えた**（明確な後退）。
案件 memory にも「まず HANDOFF.md を読む」と明記されていた——**2箇所の指示を両方素通りした**。

**恒久ルール**:
1. 案件に入ったら **①案件memory → ②README.md → ③HANDOFF等の引き継ぎ書 → ④skill** の順に全文読む。
   「skill を読んだから十分」は誤り。**案件文書のほうが具体的で優先度が高い**
2. **「無い」「未着手」と判断する前に、案件側が既に用意していないか必ず確認する**。
   探索の起点を「参考/一般論」でなく「この案件で既に決まっていること」に置く
3. 既存の成果物と**同名のディレクトリを別の場所に作らない**。版を継ぐなら既存採番の続きに
4. 「完了済み」と書かれた工程を再実行してよいのは、**その結果を疑う具体的な理由がある時だけ**。
   その場合も再実行だと明示し、前回結論との差分を報告する

**強制機構**: 案件フォークの SessionStart hook が起動時に HANDOFF の所在・pipeline status・
現在の採用版を自動注入する（`core/ops/hooks/`）。読み忘れという概念自体を消す。
